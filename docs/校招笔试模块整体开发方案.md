# 校招笔试模块整体开发方案

## 1. 文档目标

本文档用于统一「校招笔试」模块的前端页面、后端架构、数据库设计、后台管理、Excel 批量导入、分类绑定、题目渲染、刷题流程与风险控制方案，确保以下三类资料完全对齐：

1. Excel 题库模板：作为后端数据结构、导入规则、字段校验与题目渲染数据源的核心依据。
2. `校招笔试.html`：作为用户侧模块首页的视觉结构与交互参考标准。
3. 现有站点架构：基于当前项目的 `Next.js Web + NestJS API + Prisma + MySQL` 技术栈，完成低风险集成。

本文档目标不是只给出抽象思路，而是给出可直接进入研发排期和开发拆解的落地方案。

## 1.1 已确认首版决策

以下事项已由需求方确认，后续设计与开发必须严格以此为准，不再按“可选项”处理：

1. 首版即上线完整刷题与判分能力，不做“仅浏览题目 + 查看答案”的简化版。
2. 一级分类与二级分类后台管理本次一起建设，不延后。
3. 题目图片、解析图片、HTML 内嵌图片后续统一转存 OSS，不长期依赖原始外链直出。
4. 简答题首版不仅展示参考答案，还需要提供自动判分能力。

## 2. 现状与输入资料结论

### 2.1 Excel 题库模板结论

根据样例数据抽取，Excel 当前为单工作表、12 列结构，核心字段如下：

| 列序号 | 字段含义 | 说明 |
| --- | --- | --- |
| 1 | 题目 | 支持 HTML，可能包含内嵌图片 |
| 2 | 题型 | `1单选 2多选 3判断 4单项填空 5多项填空 6简答` |
| 3 | 题目类型 | `1文字 2图片` |
| 4 | 分类专项 id | 对应后台二级分类 |
| 5 | 难度 | 1-5 |
| 6 | 是否高频错题 | `0否 1是` |
| 7 | 选项 | 题目选项原始值 |
| 8 | 选项类型 | `1文字 2图片` |
| 9 | 答案 | 选择题一般为字母，填空/简答为文本 |
| 10 | 题目解析 | 支持 HTML，可能包含内嵌图片 |
| 11 | 题目图片链接 | 选填 |
| 12 | 解析图片链接 | 选填 |

已识别出的真实数据特征与开发影响如下：

1. `题目`、`选项`、`题目解析` 字段可能包含 HTML 标签，不能按纯文本直接显示。
2. HTML 内可能包含内嵌 `<img>` 外链，同时还有独立的题目图片、解析图片字段，前端必须统一图片规则。
3. 样例中 `选项` 分隔符实际出现 `|||`，与表头说明的英文分号 `;` 不完全一致，导入层必须兼容两种及更多变体。
4. 题目类型与选项类型独立存在，意味着前端不能只靠题型渲染，还要判断内容是否为图片题或图片选项。

### 2.2 前端参考页 `校招笔试.html` 结论

该 HTML 文件可视为「校招笔试模块首页」标准稿，主要由三部分组成：

1. 顶部功能卡片区：快速练习、历年试卷、智能组卷。
2. 中部专项练习区：一级分类折叠、二级分类列表、题量统计、去练习入口、自定义刷题入口。
3. 右侧信息区：练习历史、数据统计（预测分、错题、笔记、收藏）。

结论如下：

1. 该 HTML 是模块首页，并非题目详情页或答题页。
2. 前台需要新增独立模块入口，进入后默认首先展示此首页结构。
3. 答题流程、题目详情、刷题交互需在此首页之后进入独立页面，不建议把所有功能堆在首页。

### 2.3 当前项目集成结论

当前项目已具备以下基础条件：

1. 用户侧站点主导航已组件化，适合新增 `校招笔试` 导航入口。
2. 管理后台已具备成熟的 `AdminModule`、列表页、导入/治理能力扩展模式。
3. Web 侧已有富文本渲染样式基础，可复用思路，但题库模块应单独封装，避免与现有业务页面样式耦合。
4. 后端 Prisma 使用 MySQL，适合承载分类、题目、导入批次、用户做题记录等结构化数据。

## 3. 模块总体目标

「校招笔试」模块需同时满足以下四类能力：

1. 用户侧浏览与刷题：支持题库首页、分类导航、题目练习、查看答案解析、历史继续做题。
2. 后台分类管理：支持一级分类、二级分类维护，形成题目归属锚点。
3. 后台批量上传：管理员在某个二级分类下上传 Excel，本次上传题目全部自动绑定到当前二级分类。
4. 数据全链路一致：Excel 字段、数据库结构、后台导入逻辑、前台展示逻辑完全对齐。

补充后的首版范围定义如下：

1. 前台首页 + 分类页 + 刷题页 + 判分结果页一次性打通。
2. 后台分类管理 + 二级分类上下文导入 + 导入校验一次性打通。
3. 图片导入、转存、渲染、失败兜底一次性打通。
4. 简答题自动判分能力首版即建设，但判分策略需采用“规则判分优先、AI 评分兜底”的可控方案。

## 5. 分类与后台上传绑定规则

## 5.1 分类层级模型

后台严格采用两级分类：

1. 一级分类：主题类目，例如政治理论、判断推理、资料分析。
2. 二级分类：专项类目，对应 Excel 中的 `分类专项 id`。

题目不直接挂一级分类，而是始终归属于某个二级分类，一级分类由二级分类反查得到。

## 5.2 后台操作规则

后台标准流程必须固定为：

1. 先创建一级分类。
2. 再在一级分类下创建二级分类。
3. 管理员进入某一个二级分类详情页。
4. 在该二级分类上下文中执行 Excel 上传。
5. 本次上传批次中的所有题目自动归属当前二级分类。

禁止的做法：

1. 上传时再手动选择一级分类或二级分类，避免一批题目中出现混绑。
2. 在题目维度允许管理员随意改分类但不留痕，防止分类污染。

## 5.3 分类绑定规则

### 5.3.1 绑定主规则

系统以“当前进入的后台二级分类”为强绑定上下文，导入时执行以下逻辑：

1. 读取 Excel 每条题目的 `分类专项 id`。
2. 校验该 id 是否等于当前页面所属二级分类 id。
3. 若相等，则允许导入。
4. 若不相等，则整行标记失败，不允许入库。

### 5.3.2 为什么必须双重校验

虽然上传入口已经绑定当前二级分类，但仍要校验 Excel 内部 `分类专项 id`，原因如下：

1. 防止运营误把 A 分类题库传到 B 分类下。
2. 防止表格历史遗留数据未更新。
3. 防止脚本导入绕过页面上下文。

最终归属判定应同时满足：

1. 上传上下文为二级分类 B。
2. Excel 每行 `分类专项 id = B.id`。

只有同时满足才允许写入。

## 6.1 设计原则

数据库设计需要同时覆盖：

1. 分类管理
2. 题库存储
3. 导入批次
4. 导入错误记录
5. 用户练习记录

该表的用途：

1. 保留简答题评分依据，方便申诉、排错和模型调优。
2. 支持后续回放判分过程，而不污染客观题数据结构。
3. 为后台提供“主观题评分质检”入口。

## 6.3 `optionsJson` 与 `answerJson` 标准结构

### 6.3.1 选项结构

```json
[
  {
    "key": "A",
    "contentType": 1,
    "contentHtml": "<p>少儿人口</p>",
    "imageUrl": null
  }
]
```

字段说明：

1. `key`：选项字母
2. `contentType`：1文字 2图片
3. `contentHtml`：文字或富文本内容
4. `imageUrl`：图片型选项时的图片地址

### 6.3.2 答案结构

单选/判断：

```json
{
  "type": "single",
  "values": ["A"]
}
```

多选：

```json
{
  "type": "multiple",
  "values": ["A", "C"]
}
```

单项填空：

```json
{
  "type": "blank_single",
  "values": ["通货膨胀"]
}
```

多项填空：

```json
{
  "type": "blank_multi",
  "values": ["财政政策", "货币政策"]
}
```

简答：

```json
{
  "type": "essay",
  "values": ["参考答案内容"]
}
```

## 7. Excel 导入与标准化方案

## 7.1 导入总流程

标准流程如下：

1. 管理员进入某二级分类详情页。
2. 点击“上传题库”。
3. 上传 Excel。
4. 服务端解析首个工作表。
5. 校验表头与列顺序。
6. 按行执行数据标准化。
7. 校验字段合法性与分类绑定。
8. 生成预览结果与错误报告。
9. 管理员确认导入。
10. 写入题目表、导入批次表、错误明细表。
11. 回刷该二级分类题量与一级分类汇总统计。

## 7.2 表头校验规则

表头需与系统预期字段一一对应。建议采用“强校验列顺序 + 弱兼容列别名”的策略：

1. 强校验：首版按 12 列固定顺序校验，降低导入歧义。
2. 弱兼容：允许少量表头文案差异，如空格、全角括号、大小写、中文冒号等。

出现以下情况直接拦截：

1. 列数不足或超出
2. 缺失核心列
3. 题型列、分类专项 id 列、答案列被误删

## 7.3 单行数据标准化规则

### 7.3.1 通用清洗

1. 去除首尾空格
2. 将全角分号统一为半角分号
3. 将多个候选分隔符统一成系统内部标准
4. 将空字符串转为 `null`
5. HTML 实体解码
6. 去除危险标签与危险属性

### 7.3.2 选项解析规则

兼容以下分隔方式：

1. `;`
2. `；`
3. `|||`
4. 连续换行加显式分项前缀（作为兜底兼容）

若某行无法安全拆分出合法选项，整行标记失败。

### 7.3.3 图片处理规则

题目来源中可能存在三类图片：

1. 题干 HTML 内嵌图
2. 独立题目图片链接
3. 解析 HTML 内嵌图与独立解析图

导入时需：

1. 提取所有图片 URL
2. 做基础 URL 合法性校验
3. 保留原始地址
4. 将图片下载到临时存储并转存 OSS
5. 回写 OSS 地址到标准化结果
6. 记录图片数量与转存状态，便于后续巡检

图片导入链路建议为：

1. Excel 解析阶段抽取所有图片 URL。
2. 导入预览阶段先做 URL 合法性和可访问性快速检查。
3. 正式导入阶段执行“下载 -> MIME 校验 -> 上传 OSS -> 回写地址”。
4. 若转存失败：
   a. 首版建议该题整行失败，保证正式上线题库中的图片资源可控。
   b. 若该题本身不依赖图片且失败的是解析补充图，可允许按配置降级为警告，但默认仍建议失败。

OSS 转存要求：

1. 路径按 `campus-exam/questions/{questionId}/...` 组织。
2. 原图与转存图要保留扩展名与内容类型。
3. 需限制图片大小、格式、下载超时，防止恶意资源拖垮导入任务。
4. HTML 中的内嵌图片地址应在清洗后替换为 OSS 地址，而不是继续保留外链。

### 7.3.4 按题型校验答案

| 题型 | 校验规则 |
| --- | --- |
| 单选 | 答案仅允许单个字母 |
| 多选 | 答案允许多个字母，需可拆分为数组 |
| 判断 | 可兼容 `A/B`、`对/错`、`正确/错误`，入库统一标准值 |
| 单项填空 | 仅允许一个答案值 |
| 多项填空 | 允许多个答案值 |
| 简答 | 允许长文本答案 |

## 7.4 导入失败策略

建议采用“行级失败，不整批回滚”的策略，但需区分预览导入与正式导入：

1. 预览导入：全部只校验不落库。
2. 正式导入：合法行落库，非法行写错误明细。

如果失败比例过高，例如超过 30%，可提示管理员取消导入并修正源文件。

## 8. 富文本与图片渲染方案

## 8.1 渲染总体原则

题干、选项、解析不能直接显示原始 HTML 文本，必须经过“清洗 -> 标准化 -> 受控渲染”三步。

建议采用如下策略：

1. 服务端清洗脏 HTML
2. 前端统一使用 `RichContentRenderer` 渲染
3. 图片统一走 `QuestionImage` 组件
4. 所有 HTML 场景共享白名单策略

## 8.2 HTML 白名单建议

允许标签：

1. `p`
2. `br`
3. `strong`
4. `em`
5. `ul`
6. `ol`
7. `li`
8. `img`
9. `table`
10. `thead`
11. `tbody`
12. `tr`
13. `td`
14. `th`
15. `blockquote`

默认移除：

1. `script`
2. `style`
3. `iframe`
4. 所有 `on*` 事件属性
5. 非必要 `class`、`style`、`id`

## 8.3 前端图片显示规则

所有图片统一遵守：

1. 最大宽度 `100%`
2. 高度自动
3. 外层容器圆角、浅边框、浅背景
4. 居中显示
5. 移动端不允许撑破屏幕
6. 图片加载失败时显示占位卡片

占位卡片至少包含：

1. 图片图标
2. 文案“图片加载失败”
3. 原图链接查看或重试加载按钮

前端实际渲染地址优先级：

1. 优先使用转存后的 OSS 地址
2. 若 OSS 地址缺失且资源仍处于处理中，可短暂回退原始地址
3. 若两者都不可用，则进入占位态

## 8.4 页面布局防错乱规则

为防止 HTML 内容把页面撑坏，必须增加以下保护：

1. 超宽表格允许横向滚动
2. 连续图片之间保留固定间距
3. 空段落自动压缩
4. 异常长字符串强制换行
5. 图片区和答案区不混排

## 9. 6 类题型前端展示与交互

## 9.1 单选题

展示方式：

1. A/B/C/D 竖向卡片
2. 选中后高亮
3. 提交后显示正确答案与错误项

交互规则：

1. 点击即切换当前选中项
2. 未选择时不允许提交
3. 查看答案后记录为“已查看”

## 9.2 多选题

展示方式：

1. 复选卡片组
2. 已选项显示勾选样式

交互规则：

1. 支持多选/取消选择
2. 提交前提示“至少选择一项”
3. 判定采用“完全一致才正确”

## 9.3 判断题

展示方式：

1. 只显示两个大按钮：正确/错误
2. 若题库答案使用 A/B，则前端仍映射为对/错视觉

交互规则：

1. 单选提交
2. 提交后显示标准答案

## 9.4 单项填空

展示方式：

1. 单输入框
2. 可选在题干中插入视觉空位

交互规则：

1. 提交前去首尾空格
2. 支持全半角与常见标点标准化
3. 首版仅支持精确匹配或标准化后匹配

## 9.5 多项填空

展示方式：

1. 多输入框
2. 按答案顺序显示“第 1 空/第 2 空”

交互规则：

1. 逐空校验
2. 可展示每空正确与否

## 9.6 简答题

展示方式：

1. 题干 + 用户作答区 + 自动判分结果区 + 参考答案折叠区
2. 首版必须提供自动判分，不再采用仅展示参考答案的轻量模式

交互规则：

1. 用户输入文本后提交
2. 系统立即返回判分结果：正确、部分正确、错误，或进入待复核
3. 判分结果需包含得分、命中点、缺失点、参考答案与解析
4. 用户答案与判分结果需写入练习记录，支持历史回看

自动判分策略建议采用“两段式”：

1. 第一段为规则判分：
   a. 对参考答案做关键词、核心短语、同义词词典、否定词处理。
   b. 对用户答案做分词、去停用词、标点归一化、大小写归一化。
   c. 先基于命中点、遗漏点和关键短语覆盖率给出基础分。
2. 第二段为 AI 评分兜底：
   a. 当规则判分分值处于边界区间，或答案为开放性描述题时，调用模型进行语义评分。
   b. 模型输出必须受结构化约束，返回分数、结论、理由，不允许自由散漫回复。
3. 最终评分模式支持：
   a. `rule`：纯规则评分
   b. `hybrid`：规则 + AI 复核
   c. `pending_review`：系统置信度不足时进入后台复核

首版判分原则：

1. 不追求绝对教学级评分，但必须做到结果稳定、可解释、可回溯。
2. 同一答案重复提交时应尽量得到一致结果。
3. 评分理由必须可落库，避免出现“有分数没依据”。

## 15. 风险点与预案

## 15.1 数据冲突风险

### 风险 1：Excel 内 `分类专项 id` 与上传上下文不一致

后果：

1. 题目被错误归类
2. 首页分类统计错乱

预案：

1. 强校验当前 `specialId`
2. 不一致则整行失败
3. 导入预览页高亮提示

### 风险 2：表头说明与真实数据格式不一致

已发现样例选项分隔符存在不一致风险。

预案：

1. 导入层兼容多分隔符
2. 无法识别时记录错误而非静默修正

## 15.2 渲染风险

### 风险 3：HTML 源码直接露出

预案：

1. 服务端清洗
2. 前端富文本组件统一渲染

### 风险 4：图片加载失败导致布局塌陷

预案：

1. 图片统一组件
2. 固定最小高度
3. 显示占位卡片

### 风险 5：超宽表格/超大图片撑坏移动端

预案：

1. 表格外层滚动容器
2. 图片最大宽度限制
3. 异常内容强制换行

## 15.3 业务漏洞风险

### 风险 6：管理员在全局页上传导致分类归属不明

预案：

1. 只允许在二级分类详情页上传
2. 禁止提供全局无分类上传入口

### 风险 7：题型与答案结构不匹配

预案：

1. 导入时按题型校验答案
2. 不匹配则整行失败

### 风险 8：用户练习历史与题目状态无法恢复

预案：

1. 建立 `practice_sessions` 和 `practice_answers`
2. 保存 `lastQuestionId`
3. 首页“继续做题”按钮直达未完成会话

### 风险 9：外链图片转存 OSS 失败导致整批导入不可用

预案：

1. 将图片处理拆为可重试任务，保留批次级失败信息。
2. 记录失败图片 URL、失败阶段、HTTP 状态或 MIME 异常原因。
3. 后台提供“重试转存”能力。
4. 默认以 OSS 成功转存为正式导入前提，避免线上长期依赖外链。

### 风险 10：简答题自动判分不稳定或误判

预案：

1. 优先规则判分，减少模型随机性。
2. AI 评分仅在边界场景介入，并要求结构化输出。
3. 落库评分依据、关键词命中、模型解释和分数。
4. 对低置信度结果标记为 `pending_review`，进入后台质检。
5. 题目运营侧可持续补充关键词词典与评分规则。

## 19. 结论

综合两份文件与现有项目架构，本模块的正确落地方式应为：

1. 前台以 `校招笔试.html` 作为模块首页视觉标准。
2. 后台以 Excel 模板作为题库字段与导入逻辑标准。
3. 分类必须采用一级分类 + 二级分类两层结构。
4. 题库上传必须严格在“二级分类上下文”内完成。
5. 导入必须做 HTML 清洗、图片处理、题型校验、分类校验、错误落库，并将图片统一转存 OSS。
6. 前端必须统一处理富文本与图片渲染，避免乱码、标签外露、图片失效引发布局问题。
7. 首版必须支持完整刷题与判分，不再采用轻量浏览版。
8. 简答题首版必须支持自动判分，且评分结果需要可解释、可追溯。
9. 数据库、接口、前端组件、后台流程需要围绕“分类绑定 + 批量导入 + 稳定渲染 + 可恢复练习历史 + 可审计判分”统一设计。

只要按照本文档的结构实施，前端页面、后端逻辑、数据库关系、后台上传规则能够做到一致且可扩展，满足首版上线与后续扩展需要。
