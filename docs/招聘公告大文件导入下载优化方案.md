# 招聘公告大文件导入/下载优化方案

## 一、本轮已落地修复

### 1. 导入链路协议重构
- 后台招聘公告导入已从 **`base64 + JSON`** 改为 **`multipart/form-data` 真文件上传**。
- 前端不再先把 Excel 全量转成 base64，避免大文件在浏览器主线程卡顿、体积膨胀约 \(33\%\) 后再经过 `Next proxy` 与 Nest body parser。
- `apps/web/app/api/proxy/[...path]/route.ts` 已改为**流式转发请求体**，不再用 `request.text()` 整包读入大文件。
- 同时已过滤大文件上传时可能附带的 `Expect` 请求头，修复 `undici` 在代理转发 multipart 请求时的 `UND_ERR_NOT_SUPPORTED` 问题。

### 2. 后端接收与解析能力增强
- `POST /admin/jobs/import` 已切换为真正的文件上传接口，支持 `.xlsx / .xls`。
- 当前单文件限制已提升到 **50MB**，足以覆盖用户当前反馈的 **20MB** 场景。
- 后端会校验：
  - 必须上传文件；
  - 扩展名必须为 `.xlsx / .xls`；
  - 文件大小不能超过 50MB；
  - 模板列头必须严格匹配系统模板。

### 3. 批量入库性能优化
- 导入逻辑已从“逐行串行 `create`”升级为：
  - 先做行级标准化与校验；
  - 再按 **200 行一批** 使用 `createMany` 批量写入；
  - 若某个批次写库失败，再自动降级为逐条写入并回收具体错误行。
- 这样兼顾了：
  - 大文件导入速度；
  - 行级错误定位能力；
  - 批量成功时的数据库写入效率。

### 4. 前端交互与异常提示补齐
- 后台 `招聘公告管理 -> 批量工具` 已新增：
  - 文件大小展示；
  - 上传/处理中进度条；
  - 当前状态文案（上传中、处理中、完成、失败）；
  - 最近一次导入结果中的 **总行数 / 成功 / 失败 / 耗时**；
  - 全局 toast 异常提示，避免再出现“点击开始导入没有任何反馈”的静默失败。

## 二、本轮实测结果

### 1. 小文件回测
- API 直连导入：成功。
- 经前端 `/api/proxy` 代理导入：成功。

### 2. 20MB 目标场景回测
- 已生成标准招聘公告 Excel：`/tmp/offer360-import-20mb.xlsx`
- 文件大小：**20,094,386 字节**
- 通过前端代理链路调用：`POST /api/proxy/admin/jobs/import`
- 实测结果：
  - HTTP 状态：**201**
  - 导入结果：**10000 行全部成功**
  - 服务端处理耗时：**2599ms**
  - curl 总耗时：约 **3.0 秒**

## 三、根因总结

本次“20M 文件点击开始导入无响应”的根因不是单点，而是多点叠加：

1. **前端先把 Excel 转 base64**，大文件会先在浏览器主线程卡顿；
2. **base64 再包成 JSON**，体积显著膨胀；
3. **Next 代理原实现用 `request.text()` 整包读取**，大文件再次放大内存压力；
4. **失败提示没有稳定展示到页面**，用户主观感受就是“完全没反应”；
5. 大文件请求在代理转发时附带的 `Expect` 头还会触发额外运行时异常。

## 四、下一阶段推荐优化方案

> 本轮已先完成“让 20MB 大文件稳定可用”的止血与增强。若要继续支撑更大文件与更高并发，建议按以下二期方案推进。

### 1. 大文件导入：分片上传 + 断点续传
- 前端将大文件切成固定大小分片（建议 `5MB ~ 10MB`）；
- 为每次导入生成 `uploadId`；
- 后端按分片顺序暂存并记录已上传偏移；
- 中断后只补传缺失分片；
- 所有分片完成后再触发服务端解析任务。

**收益**：
- 单次请求压力更低；
- 网络抖动时不必整文件重传；
- 适合未来扩展到 `100MB+` 文件。

### 2. 异步任务队列化导入
建议新增独立导入任务模型，例如：
- `admin_import_jobs`
- `admin_import_job_chunks`
- `admin_import_job_errors`

任务状态建议：
- `UPLOADING`
- `PENDING`
- `PROCESSING`
- `SUCCESS`
- `PARTIAL_SUCCESS`
- `FAILED`

前端提交文件后只拿到任务 ID，后端异步处理：
- 解析 Excel；
- 行级校验；
- 批量入库；
- 错误明细落库；
- 前端轮询或 SSE/WebSocket 获取进度。

### 3. 进度展示升级
当前进度条已支持“上传中 / 处理中”的基础反馈；二期建议升级为：
- 上传百分比；
- 服务端解析百分比；
- 已处理行数 / 总行数；
- 成功数 / 失败数实时刷新；
- 最近任务列表；
- 可下载错误明细 Excel。

### 4. 服务配置优化
建议后续显式收口配置：
- Web 代理层最大 body；
- API 网关 / Nginx `client_max_body_size`；
- Node 请求超时；
- 任务执行超时；
- 容器内存与 CPU 配额；
- 生产环境上传专用路由与限流策略。

### 5. 数据库写入优化
当前已采用 `createMany + 批失败降级逐条`；后续还可继续增强：
- 分批大小动态调优；
- 导入前做字段预清洗，减少 DB 端报错；
- 将错误明细落独立表，而不是只回前 20 条；
- 重要索引延迟维护或异步刷新；
- 超大导入时按任务批次号打标签，便于回滚与审计。

### 6. 大文件下载优化
当前招聘公告导出仍是“生成完整 Excel 后返回”；若未来导出规模继续放大，建议升级为：
- 后端流式写出（streaming）；
- 导出任务异步生成；
- 结果写对象存储；
- 下载接口支持断点续传 / Range；
- 导出文件设置有效期与后台下载记录。

## 五、当前结论

**本轮目标已经达成**：
- 20MB 招聘公告 Excel 不再“点击开始导入无响应”；
- 前端会展示明确进度与失败提示；
- 后端已具备更适合大文件的接收与分批入库能力；
- 代理链路的关键大文件兼容问题已修复。
