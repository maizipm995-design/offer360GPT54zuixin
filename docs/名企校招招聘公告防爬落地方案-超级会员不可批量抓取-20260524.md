## 补充确认（2026-05-25）
- 首页必须继续保留 `SSR 服务端渲染`，这是 SEO 效果的核心前提，不能为了防爬改成纯客户端首屏渲染。
- 防爬策略必须建立在 `保留 SSR` 的前提下实施：允许首页首屏输出可被搜索引擎消费的公开摘要内容，但不允许首屏直接暴露高价值真实链接资产。
- 首页初次数据拉取规范调整为：
  - 仅拉取基础常规摘要字段
  - 不拉取 `announcementUrl`
  - 不拉取 `deliveryUrl`
  - 不拉取其他任何真实源链接、可复用跳转链接、长期有效访问链接
- 各类链接资源统一延后处理：
  - 只有当用户实际点击“查看公告”“立即投递”等动作时
  - 才单独发起受控请求
  - 由后端按权限、频控、风控、审计规则返回短时受控结果
- 因此，首页正确形态不是“取消 SSR”，而是：`保留 SSR，但 SSR 只输出公开摘要，不输出真实链接与完整高价值数据。`

## 当前实现事实

### 1. 首页会直接拉取招聘公告列表
- 首页服务端渲染时直接调用 `serverGet('/jobs')` 获取岗位列表。
- 这意味着未登录访客首次打开首页时，就能拿到第一批招聘公告数据。
- 由于这是 SSR 输出，爬虫不需要执行复杂 JS，就能直接从 HTML 或后续接口中拿到数据。

### 2. 岗位列表接口当前是公开接口
- `GET /jobs` 无鉴权。
- `GET /jobs/:id` 无鉴权。
- `GET /jobs/suggestions` 无鉴权。
- 当前后端没有对 `jobs:list:view`、`jobs:detail:view`、`jobs:search:use`、`jobs:filter:use` 做强制校验。

### 3. 前端存在“会员限制”，但主要停留在交互层
- 前端在查看公告、搜索、筛选、立即投递时有权限判断。
- 但这些限制主要发生在 `jobs-page-client.tsx` 的按钮点击和交互逻辑中。
- 只要直接请求接口，仍可绕过前端按钮限制。

### 4. 返回给前端的字段较完整
- 列表接口当前返回的岗位对象包含：
  - 企业名称
  - 岗位名称
  - 工作地点
  - 学历要求
  - 企业性质
  - 招聘类型
  - 专业要求
  - 截止时间
  - `announcementUrl`
  - `deliveryUrl`
  - `announcementTitle`
  - 行业
  - 毕业届别
- 其中 `announcementUrl`、`deliveryUrl` 属于高价值字段，一旦被批量抓取，第三方几乎可以直接复用你们整理过的招聘公告资产。

### 5. 接口支持分页与检索，具备批量枚举条件
- `GET /jobs` 支持 `page`、`limit`，单次上限为 `50`。
- 支持关键词、城市、学历、企业性质、招聘类型等筛选组合。
- 这意味着爬虫可以稳定翻页、批量遍历、低成本收集数据库中的公开招聘公告。

### 6. 前端代理接口本质是透明转发
- 浏览器端请求 `/api/proxy/jobs`，服务端会直接转发到后端接口。
- 代理层没有对 `jobs` 相关接口额外加签、限流、验证码或权限校验。
- 因此外部爬虫既可以抓页面，也可以直接模拟前端接口批量拉数据。

## 风险结论

### 总体判断
- 当前风险等级：`高`

### 根因
- 招聘公告列表数据对匿名访客公开。
- 首页 SSR 直接输出首批数据，降低了抓取难度。
- 接口支持标准分页和筛选，便于批量采集。
- 前端权限限制没有对应的后端强校验。
- 高价值字段 `announcementUrl`、`deliveryUrl` 已直接下发到前端。

## 可能的被爬方式
- 抓首页 HTML，直接解析 SSR 首屏岗位数据。
- 直接调用 `/api/proxy/jobs?page=1&limit=20` 持续翻页采集。
- 利用城市、学历、企业性质、招聘类型做分片采集。
- 直接消费 `announcementUrl` 和 `deliveryUrl`，快速复用你们整理好的公告资产。

## 业务影响
- 数据资产被低成本搬运。
- SEO 与内容竞争压力上升。
- 会员价值和平台壁垒被削弱。
- 翻页抓取、筛选抓取、关键词采集会增加数据库与接口压力。

## 方案定位
- 本方案基于新的防护目标重新设计：`即使用户购买了超级会员，也不能通过系统批量爬走招聘公告数据。`
- 这里的“不能批量爬走”不代表绝对无法被人工查看、截图、录屏或极低速抄录。
- 本方案追求的目标是：`让任何账号都只能逐条受控消费数据，无法通过接口、翻页、详情链路把数据库中的公告批量导出。`

## 最终目标
1. 匿名用户不能批量获取招聘公告数据
2. 免费用户不能绕过前端直接拿到完整公告内容
3. 标准会员只能获得有限查看能力，不能批量提取
4. 超级会员也只能逐条受控查看，不能通过接口批量拉取
5. 所有高价值数据访问都可审计、可限速、可熔断、可追踪

## 核心原则

### 原则 1：会员权益不等于数据导出权限
- 超级会员的权益定义应当是：
  - 可以逐条查看
  - 可以逐条投递
  - 可以使用更高阶功能
- 但不等于：
  - 可以批量拉取公告详情
  - 可以批量获取真实源链接
  - 可以通过翻页接口搬走整库数据

### 原则 2：任何真实公告数据都不应通过列表接口批量下发
- 列表接口只能给摘要、状态、权限态。
- 真实公告链接、真实投递链接、完整正文、完整详情，不进入列表响应。

### 原则 2.1：首页必须保留 SSR，但 SSR 只承载公开摘要
- 首页继续使用 SSR 输出首屏内容，确保 SEO 基础能力不受影响。
- SSR 首屏只允许输出：
  - 统计数据
  - 筛选项
  - 少量公开摘要样例
- SSR 首屏禁止输出：
  - `announcementUrl`
  - `deliveryUrl`
  - 任意真实源站跳转链接
  - 可被批量复用的完整岗位详情数据
- 这样做的目标不是削弱 SEO，而是把首页 HTML 控制在“可收录但不可批量搬运”的边界内。

### 原则 3：所有高价值访问都必须变成单条、短时、受控行为
- 用户每点开一次公告，都应该是一次单独授权行为。
- 这次授权行为必须带：
  - 权限校验
  - 频控
  - 风控判断
  - 审计日志
  - 可追踪标记

### 原则 4：系统可以允许“可查看”，但不能允许“可批量搬运”
- 这是本方案和之前普通会员权限方案的最大区别。

## 风险重新定义

### 当前真正要防的不是“看一条”
- 单个用户点开 1 条、2 条、10 条公告，这属于正常消费行为。

### 真正要防的是以下行为
- 短时间连续翻页抓取列表
- 批量请求岗位详情
- 自动化脚本连续点击“查看公告”
- 抓取真实公告 URL 并离线保存
- 使用多个 IP / 多账号 / 多设备轮询采集
- 顺序枚举岗位 ID 导出全站公告

## 最终建议架构

## 一、列表层只提供“摘要数据”，不提供“真实数据出口”

### 目标
- 即使接口被抓，也只能拿到低价值摘要，拿不到真实公告资产。

### 列表层允许返回的数据
- 企业名称
- 岗位名称
- 城市或地区摘要
- 学历要求
- 企业性质
- 招聘类型
- 更新时间
- 是否存在公告
- 是否存在投递入口
- 当前用户是否具备“申请查看公告”的资格
- 当前用户是否具备“申请投递”的资格

### 列表层禁止返回的数据
- `announcementUrl`
- `deliveryUrl`
- `recruitmentLink`
- 完整公告正文
- 可直接复用的源链接
- 可长期保存的直链令牌

### 结果
- 即使超级会员抓 `/jobs?page=1...N`，也只能拿到摘要，不能直接拼出公告真实链接库。

## 二、详情层改为“受控访问申请”，不是“公开详情接口”

### 目标
- 所有高价值数据只允许逐条申请，不允许批量拉取。

### 接口形态建议
- 不再让 `GET /jobs/:id` 成为可直接拿完整详情的公开数据口。
- 改为两层结构：

#### 第一层：详情摘要接口
- 返回脱敏后的详情信息
- 可用于页面展示基础内容
- 不包含真实源链接和可批量复用数据

#### 第二层：受控查看公告接口
- 例如：
  - `POST /jobs/:id/view-announcement`
  - 或 `POST /jobs/:id/request-announcement-access`

### 受控接口执行流程
1. 识别当前用户身份
2. 校验用户是否具备查看权限
3. 校验当前账号是否超出速率阈值
4. 校验当前 IP / 设备 / 会话是否命中风控
5. 记录审计日志
6. 生成一次性访问凭证
7. 返回受控跳转结果

## 三、超级会员也不能直接拿到真实源链接

### 关键结论
- 超级会员可以“看”，但不应该直接“拿到源链接库”。

### 推荐实现方式

#### 方式 A：服务端 302 中转
- 前端请求“查看公告”
- 服务端校验通过后，直接由服务端跳到目标公告地址
- 前端不接收原始源链接字符串

#### 方式 B：站内受控预览页
- 服务端抓取或映射可展示内容
- 在站内受控页面展示
- 页面不暴露真实源站 URL

### 推荐优先级
- 第一优先：`服务端 302 中转`
- 第二优先：`站内受控预览页`

### 原因
- 302 中转更快落地，改造成本相对更低
- 站内预览更安全，但实现成本更高

## 四、把“查看公告”改成一次性、短时、单条访问凭证

### 目标
- 阻断“拿到一个长期有效 URL 就可以离线批量复用”的路径。

### 建议机制
- 每次点击查看公告时，由服务端生成：
  - 单条岗位 ID 绑定
  - 单用户绑定
  - 单设备或单会话绑定
  - 短时有效
  - 一次性消费

### 建议凭证属性
- 有效期：`30 秒 - 120 秒`
- 仅可使用：`1 次`
- 超时失效
- 二次访问必须重新申请

### 价值
- 即使凭证被抓包，也很难形成批量长期复用的数据出口。

## 五、给超级会员加“可消费上限”，不是“无限制直通”

### 目标
- 防止会员账号变成“合法爬虫账号”。

### 建议规则

#### 账号级速率限制
- 每分钟最多申请查看公告链接 `6` 次，以及申请投递入口 `6` 次
- 每 10 分钟最多申请查看公告链接 `30` 次，以及申请投递入口 `30` 次
- 每小时最多申请查看公告链接 `100` 次，以及申请投递入口 `100` 次

#### 账号级日上限
- 每日可查看公告链接 `200` 次
- 每日可申请投递入口 `200` 次

### 建议理解方式
- 这里不是为了“克扣会员权益”
- 而是为了区分：
  - 正常求职行为
  - 自动化批量采集行为

### 默认建议
- 标准会员：较低查看额度
- 超级会员：更高额度，但仍然有上限
- 所有会员：都不存在“无限次高速抓取权”

## 六、风控判断必须在服务端，不依赖前端

### 目标
- 避免脚本绕过前端按钮逻辑直接请求接口。

### 必做风控信号
- 单账号短时高频查看
- 单 IP 短时高频查看
- 单设备短时高频查看
- 规律性翻页行为
- 顺序枚举岗位 ID
- 深夜长时间连续请求
- 多账号共用同 IP / 同设备抓取
- 多 IP 轮换使用同一账号抓取

### 风控分级动作

#### 一级
- 轻度限速
- 增加冷却时间

#### 二级
- 触发验证码或二次验证
- 临时禁止查看公告

#### 三级
- 临时冻结该账号的公告访问能力
- 冻结该 IP / 设备一段时间

#### 四级
- 人工审核
- 永久封禁异常账号

## 七、必须保留完整审计日志

### 目标
- 让每一条高价值访问都可追踪。

### 建议记录字段
- 用户 ID
- 会员等级
- 岗位 ID
- 请求时间
- IP 地址
- User-Agent
- 设备标识
- 会话 ID
- 请求结果
- 是否命中限流
- 是否命中风控
- 访问凭证 ID
- 最终跳转目标类型

### 审计用途
- 回溯异常账号行为
- 调整风控阈值
- 对外部泄露事件做来源定位

## 八、增加泄露追踪能力

### 目标
- 即便发生搬运，也能尽量反查来源。

### 建议手段

#### 软水印
- 对不同账号生成不同追踪参数
- 对不同访问链路附加不同标记

#### 蜜罐链接
- 对异常账号或疑似爬虫请求返回特殊追踪标记
- 一旦外部站点出现该标记，可快速锁定泄露来源

#### 差异化令牌
- 每个账号获得的查看凭证结构不同
- 不同账号的中转链路参数不同

## 九、首页 SSR 改成“防批量抓取友好模式”

### 目标
- 减少搜索引擎和普通爬虫从首屏 HTML 直接拿走岗位数据的风险。

### 建议做法
- 首页 SSR 只输出：
  - 统计数据
  - 筛选选项
  - 极少量公开摘要样例
- 首页继续保持 SSR，不改成纯客户端首屏渲染
- 不直出完整岗位列表
- 不在 HTML 中输出任何真实公告 URL
- 不在首页初始请求中拉取任何公告链接、投递链接、真实源链接
- 链接相关资源必须在用户实际触发操作后，再走单独受控请求获取

### 推荐结果
- 首屏仍有内容，不影响页面基础感知
- 但 HTML 本身不再是公告数据仓库

## 十、接口层与入口层都要限流

### API 层限流
- `/jobs`
- `/jobs/:id`
- `/jobs/suggestions`
- `/jobs/:id/view-announcement`
- `/jobs/:id/deliver`

### Nginx 层限速
- 对匿名访问做更严格限制
- 对高频接口做 burst 控制
- 对异常 UA 和异常 IP 做黑名单处理

### 设计原则
- API 层负责业务语义限流
- Nginx 层负责流量洪峰拦截
- 两层都要有，不能只做一层

## 落地实施方案

## 第一阶段：先堵住“批量导出入口”

### 目标
- 先把最危险的链路堵住，避免继续裸奔。

### 要做的事
1. 列表接口移除真实 `announcementUrl` / `deliveryUrl`
2. 详情接口不再直接返回完整真实公告数据
3. 前端列表与详情页改成受控申请查看
4. 首页 SSR 不再直出完整岗位列表

### 预期收益
- 立刻降低批量采集成功率
- 立刻降低列表接口被直接复用的价值

## 第二阶段：把“查看公告”改成单条受控消费

### 要做的事
1. 新增查看公告申请接口
2. 增加一次性短时凭证
3. 增加服务端中转
4. 增加申请成功与失败日志

### 预期收益
- 即便是超级会员，也无法通过一次请求直接拿到一批可复用链接

## 第三阶段：加入账号级频控与日额度

### 要做的事

### 预期收益

### 要做的事

3. 设计来源反查方案

### 预期收益
- 一旦发生外部搬运，可以更快定位问题账号和路径

## 权限模型建议

### 匿名用户
- 可看公开摘要
- 不可看真实公告
- 不可拿真实源链接

### 免费用户
- 可看公开摘要
- 可看少量详情摘要
- 不可看真实公告
- 不可拿真实源链接

### 标准会员
- 可逐条申请查看公告
- 可逐条申请投递
- 有速率限制
- 有日额度限制
- 不能批量导出

### 超级会员
- 可获得更高的逐条查看额度
- 可获得更高的投递额度
- 可用高级功能
- 仍然不能批量导出
- 仍然受限流、风控、审计约束

## 明确禁止的系统能力
- 不提供公告批量导出
- 不提供真实公告 URL 列表导出
- 不提供永久有效查看链接
- 不提供全量详情翻页接口
- 不允许任何会员角色获得“整库可拉取”能力

## 推荐默认产品规则
1. 超级会员也没有无限次查看权，只有更高额度
2. 查看公告统一走服务端受控中转
3. 列表接口永久不返回真实公告链接
4. 高价值访问必须带审计日志
5. 高频行为必须触发限流与风控

## 验收标准
- 匿名抓列表接口，拿不到真实公告 URL
- 免费用户直接调接口，也拿不到完整真实公告
- 超级会员连续批量点击查看公告时，会触发限速或熔断
- 任意账号都无法通过标准翻页接口导出完整公告库
- 查看公告链路全部可追踪、可审计
- 异常访问可被封禁和复盘

## 具体实施清单

## 第一阶段：先堵住批量导出入口

## 最终结论
- 可以把系统设计成：`超级会员可以逐条消费招聘公告，但永远不能获得批量提取数据库公告的能力。`
- 真正的落地关键不是“隐藏按钮”，而是：
  - 列表不下发真实数据
  - 详情不公开直出
  - 查看公告必须单条受控申请
  - 所有高价值访问都有限流、风控、审计和追踪
- 这套方案能显著抬高批量采集成本，并把超级会员从“高权限爬虫账号”改造成“高额度但受控的正常消费账号”。
