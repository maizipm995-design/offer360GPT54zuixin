# Offer360 数据库迁移与回滚规范

## 为什么必须改成 Migration
当前项目已经切换到 Prisma migration 流，目的不是“方便建表”，而是保证：
- 每一次数据库结构变化都有脚本留痕
- 生产发布时只执行增量结构变更，不覆盖线上业务数据
- 结构变更可审计、可追溯
- 应用发布、数据库变更、业务数据三者解耦

## 当前约定
- Prisma schema 文件：`apps/api/prisma/schema.prisma`
- Migration 目录：`apps/api/prisma/migrations`
- 基线迁移：`202605080001_baseline`
- 锁文件：`apps/api/prisma/migration_lock.toml`

## 开发环境如何改表
### 1. 修改 Prisma Schema
- 先改 `apps/api/prisma/schema.prisma`

### 2. 生成开发迁移
```bash
npm run db:migrate -- --name <本次变更名>
```

说明：
- `db:migrate` 对应 `prisma migrate dev`
- 该命令会在 `apps/api/prisma/migrations` 下生成新迁移目录
- 同时更新 Prisma Client

### 3. 本地验证
```bash
npm run db:generate
npm run build:api
```

## 生产环境如何执行迁移
生产环境禁止使用以下方式：
- `prisma db push`
- 手工删除表再重建
- 直接导入全量 SQL 覆盖线上库

生产环境只允许：

```bash
npm run db:migrate:deploy
```

在自动化部署中，该命令由 `deploy/prod/scripts/deploy-release.sh` 通过 `migrator` 容器自动执行。

## 基线迁移说明
项目之前没有正式的 Prisma migration 目录，因此本次改造新增了基线迁移：
- 从当前 `schema.prisma` 自动生成
- 作为后续所有增量变更的起点

如果线上数据库已经存在并且结构与当前 schema 一致，首次接入时建议先在受控环境完成一次验证，再切生产发布。

## 回滚原则
### 应用回滚
- 当前交付支持蓝绿槽位应用回滚
- 可以快速把流量切回上一稳定版本

### 数据库回滚
- 不建议把数据库回滚理解为“像应用一样一键切回”
- 生产数据库一旦发生 destructive migration，旧应用未必还能继续兼容

因此数据库回滚规范如下：
- 优先做向后兼容迁移
- 优先两阶段发布
- 非必要不要在单次发布里做删除列、改类型、重命名列这类破坏性操作

## 推荐迁移策略
### 1. 新增字段
- 先加 nullable 字段或带默认值字段
- 先发布兼容新旧字段的应用版本
- 数据回填完成后，再做下一步约束收紧

### 2. 删除字段
- 第一步：应用不再读取旧字段
- 第二步：确认线上已经不依赖旧字段
- 第三步：单独发布 migration 删除字段

### 3. 改字段类型
- 优先新建新字段并双写
- 完成回填后切读新字段
- 最后再删除旧字段

## 提交要求
- 每次数据库结构变更必须提交：
  - `schema.prisma`
  - 新生成的 migration 目录
  - 如有需要，配套的数据回填脚本
- 禁止只改 `schema.prisma` 不提交 migration

## 常用命令
### 查看迁移状态
```bash
npm run db:migrate:status
```

### 开发环境快速同步（仅本地调试）
```bash
npm run prisma:db:push --workspace @offer360/api
```

说明：
- `db push` 只允许在本地临时调试场景使用
- 禁止放进生产发布流程

### 生产环境迁移
```bash
npm run db:migrate:deploy
```

## 发布前检查清单
- 已提交 migration 目录
- 已在本地开发库验证 migration 可执行
- 已确认本次 migration 不会覆盖业务数据
- 若有破坏性变更，已采用兼容式两阶段迁移
- 已准备好应用回滚预案
