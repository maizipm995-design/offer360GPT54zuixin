# Offer360 会员体系最终定稿方案

## 一、方案结论（最终拍板口径）

- **角色命名固定**：C 端用户角色统一收敛为 `免费用户`、`标准会员`、`超级会员` 三档；展示名和内部编码都固定，不允许后期随意改名，避免运营、研发、客服口径混乱。
- **内部编码固定**：分别为 `FREE_USER`、`STANDARD_MEMBER`、`SUPER_MEMBER`。
- **权限继承固定**：`SUPER_MEMBER` 自动继承 `STANDARD_MEMBER` 的全部权限；`STANDARD_MEMBER` 自动继承 `FREE_USER` 的基础站点访问能力；`FREE_USER` 不拥有任何核心求职权限。
- **权限控制方式固定**：所有核心求职能力统一收敛为**权限字典 + 角色绑定 + 前后端双重校验**，不再在页面里散落写死 `isMember` 条件。
- **后台配置方式固定**：后台新增独立的 **C 端角色权限配置页**，只维护这三种固定角色与权限勾选关系；角色名称、角色编码不可编辑，避免体系失控。
- **按钮策略固定**：无权限按钮**不隐藏**，保持可见；用户点击时统一提示并引导开通或升级会员。
- **与当前系统关系**：现有后台管理员 RBAC（`admin_users / admin_roles / admin_role_permissions`）继续只服务后台；本次新增的是 **C 端会员角色权限体系**，两套权限域严格隔离，不能混用。
- **现有布尔会员口径废弃**：当前前后端大量使用的 `isMember` 只能表达“是否存在有效会员”，无法表达“标准 / 超级”的差异；后续必须升级为“角色 + 权限”模型，`isMember` 仅保留为兼容字段或派生字段。
- **与专属推荐关系**：自本方案生效后，`专属推荐`、`查看内推码`、`标记求职进度` 三项能力统一归属 `SUPER_MEMBER`，不再使用模糊的“会员专属”口径。

## 二、PRD（最终定稿版）

### 2.1 背景与问题

当前项目已经具备会员开通、兑换码、会员剩余天数展示、后台管理员角色权限等基础能力，但 C 端会员体系仍存在明显缺口：

- 当前只有粗粒度字段 `isMember`，无法区分 `标准会员` 与 `超级会员`；
- `jobs` 页内的搜索、筛选、投递、内推、进度、推荐等能力目前没有形成统一权限矩阵；
- 会员门槛散落在前端按钮点击和个别后端接口里，规则不集中、容易遗漏；
- 后台虽然有管理员 RBAC，但缺少面向 C 端用户权益的“角色权限配置”页面；
- 产品侧对会员权益的表述已经明显超出当前系统表达能力，继续沿用 `isMember` 会导致实现和文案长期失真。

因此，本次定稿目标不是简单“补几个判断”，而是建立一套**命名统一、角色清晰、权限颗粒化、可后台配置、可前后端统一执行**的会员体系底座，为后续 `专属推荐`、`内推码`、`求职进度`、更多增值权益提供统一治理方式。

### 2.2 产品目标

#### 2.2.1 核心目标

- **统一命名**：所有人都只使用 `免费用户 / 标准会员 / 超级会员` 三种说法。
- **统一权限**：所有核心求职能力都能映射到明确权限码，不再模糊依赖“是不是会员”。
- **统一继承**：超级会员天然包含标准会员能力，避免重复配置与重复判断。
- **统一后台**：运营能在后台通过勾选方式调整角色权限组合，而不是找研发改代码。
- **统一风控**：前端可见即可点，但后端必须二次校验，防止抓包绕过。
- **统一扩展**：后续新增“新会员权益”时，只要接入权限字典，就能沿用相同机制继续扩展。

#### 2.2.2 业务目标

- 建立更清晰的付费梯度：
  - `标准会员` 承接“找岗、筛选、查看、投递”主需求；
  - `超级会员` 承接“高效求职、专属推荐、内推、进度管理”高阶需求。
- 降低运营和客服解释成本，避免用户理解“会员到底能干什么”时产生歧义。
- 为后续会员转化、升级转化、权限 AB 调整、投放活动提供可配置底座。

### 2.3 角色定义（固定不可混乱）

| 角色展示名 | 内部编码 | 角色定位 | 是否系统固定 | 备注 |
|---|---|---|---|---|
| 免费用户 | `FREE_USER` | 注册默认身份，仅可浏览首页和基础公开内容 | 是 | 不可删除、不可改名 |
| 标准会员 | `STANDARD_MEMBER` | 开放基础找岗与投递能力 | 是 | 不可删除、不可改名 |
| 超级会员 | `SUPER_MEMBER` | 全权限会员，解锁高阶求职增值能力 | 是 | 不可删除、不可改名 |

### 2.4 角色权益明细

#### 2.4.1 免费用户

- **可用范围**：仅首页基础浏览、公开品牌内容、会员购买页、登录注册、求职服务营销内容。
- **明确限制**：
  - 不可浏览招聘公告完整列表；
  - 不可使用岗位搜索；
  - 不可使用岗位筛选；
  - 不可查看招聘公告详情；
  - 不可立即投递；
  - 不可查看内推码；
  - 不可标记求职进度；
  - 不可进入 `专属推荐`。
- **产品总结**：免费用户只能感知平台基础内容与会员价值，核心求职功能全部锁定。

#### 2.4.2 标准会员

- **开放能力**：
  - 浏览全网招聘公告；
  - 正常使用岗位搜索、筛选、查询；
  - 查看完整招聘公告详情；
  - 正常使用立即投递。
- **明确限制**：
  - 不可查看内推码；
  - 不可标记求职进度；
  - 不可进入 `专属推荐`。
- **产品总结**：标准会员解决“看岗位 + 找岗位 + 投岗位”的主链路。

#### 2.4.3 超级会员

- **开放能力**：
  - 继承标准会员全部能力；
  - 解锁查看内推码；
  - 解锁标记求职进度；
  - 解锁 `专属推荐`。
- **产品总结**：超级会员覆盖全站求职闭环，是完整增值权益角色。

### 2.6 权限继承规则

#### 2.6.1 固定继承关系

- `FREE_USER`：无核心求职权限；
- `STANDARD_MEMBER`：在 `FREE_USER` 的基础站点访问能力之上，新增基础求职权限；
- `SUPER_MEMBER`：自动继承 `STANDARD_MEMBER` 全部权限，再额外新增 `referral / progress / recommend` 三项高阶权限。

#### 2.6.2 判定原则

- **角色判定优先级**：`SUPER_MEMBER > STANDARD_MEMBER > FREE_USER`；
- **权限生效方式**：
  \[
  有效权限 = 当前角色自有权限 \cup 父角色继承权限
  \]
- **系统角色不可改名不可删除**，只允许调整“当前角色拥有哪些权限项”；
- **禁止人工取消继承关系**，防止出现“超级会员反而没有标准会员能力”的脏配置。

### 2.7 生命周期规则

#### 2.7.1 注册默认规则

- 用户注册成功后默认归属 `FREE_USER`；
- `FREE_USER` 不需要单独写入会员记录；
- 没有有效会员记录的用户，统一按 `FREE_USER` 处理。

#### 2.7.2 开通规则

- 开通标准会员后，角色变为 `STANDARD_MEMBER`；
- 开通超级会员后，角色变为 `SUPER_MEMBER`；
- 开通来源支持：
  - 前台直购；
  - 兑换码兑换；
  - 后台人工开通。

#### 2.7.3 续费规则

- 当前为标准会员：允许续标准，也允许升级为超级；
- 当前为超级会员：允许续超级；
- **禁止用低等级权益覆盖高等级生效权益**，即超级会员有效期内，不允许通过前台或兑换码把角色降回标准会员；
- 后台保留人工干预能力，可在客服/运营场景下执行强制调整。

#### 2.7.4 升级规则

- 标准会员升级超级会员时：
  - 角色立即切换为 `SUPER_MEMBER`；
  - 剩余有效期保留；
  - 新购时长继续叠加到当前 `endAt`。

#### 2.7.5 过期规则

- 会员过期后，用户角色自动回退为 `FREE_USER`；
- 过期后立即失去全部会员权限；
- 任何依赖角色权限的接口都必须实时按服务端当前时间重新判定，不允许仅信任客户端缓存。

### 2.8 交互与页面规则

#### 2.8.1 总体交互原则

- 无权限按钮**不隐藏**；
- 点击时统一提示“当前权益仅对对应会员开放”；
- 提示弹窗需明确给出：
  - 当前能力名称；
  - 需要的目标角色；
  - “立即开通 / 立即升级”主按钮；
  - 跳转目标：`/membership`。

#### 2.8.2 `jobs` 页规则

- 免费用户：
  - 可以进入 `jobs` 页外壳，但列表区不下发完整数据；
  - 搜索、筛选、查看公告、立即投递、查看内推、更新进度、专属推荐均触发会员引导；
  - 页面主视觉保留会员权益卡与转化信息。
- 标准会员：
  - 可以正常使用列表、搜索、筛选、详情和投递；
  - 点击“查看内推”“求职进度”“专属推荐”时，统一提示升级为超级会员。
- 超级会员：
  - 开放全部招聘公告相关能力。

#### 2.8.3 个人中心规则

- 会员信息区需明确展示：
  - 当前角色；
  - 到期时间；
  - 剩余天数；
  - 若为标准会员，展示“升级超级会员”入口；
  - 若为超级会员，展示“续费超级会员”入口。

#### 2.8.4 会员开通页规则

- 会员页需明确区分 `标准会员` 与 `超级会员` 两档卡片；
- 卡片上分别展示对应权益差异；
- 若当前为标准会员，超级会员卡主按钮文案应为“升级超级会员”；
- 若当前为超级会员，标准会员卡需置灰或说明“当前不可降级购买”。

### 2.9 后台配置产品方案

#### 2.9.1 页面定位

后台新增 **`用户角色权限配置`** 页面，专门服务 C 端会员角色，不与后台管理员角色页混用。

建议路径：`/admin/member-roles`

#### 2.9.2 页面结构

- **区域 A：权限字典区**
  - 展示权限码、权限名称、说明、所属模块、排序；
  - 系统内置权限码不可删除、不可改 code；
  - 可维护文案说明和展示顺序。
- **区域 B：角色权限矩阵区**
  - 固定三行：免费用户 / 标准会员 / 超级会员；
  - 每列一个权限项；
  - 勾选代表该角色拥有该权限；
  - 超级会员行额外显示“继承标准会员全部权限”。
- **区域 C：变更说明与预览区**
  - 预览每个角色当前拥有的最终权限；
  - 保存前提示“本次变更会影响哪些前台能力”。

#### 2.9.3 配置边界

- 允许改：角色拥有的权限项；
- 不允许改：角色编码、角色名称、继承链、系统角色数量；
- 允许新增权限项元数据，但**只有已经被前后端接入的权限码才会真正生效**；
- 对“全新业务能力”的权限支持，仍需研发先接入权限判断逻辑，后台只是配置载体，不是无代码平台。

### 2.10 验收标准（产品口径）

- 免费用户无法使用任何核心求职能力；
- 标准会员可完成“看岗位 + 搜岗位 + 筛岗位 + 看详情 + 投递”；
- 超级会员可额外完成“看内推 + 标进度 + 用推荐”；
- 超级会员自动拥有标准会员全部能力；
- 后台可通过勾选切换角色权限，无需改业务代码中的 if/else 文案判断；
- 前端点击拦截与后端接口拦截口径一致；
- 任何已过期会员都不能继续使用原有会员能力。

## 三、技术实施方案（最终定稿版）

### 3.1 技术方案总原则

- **权限域隔离**：后台管理员权限体系与 C 端会员权限体系分离建模；
- **角色固定、权限可配**：角色是系统常量，权限绑定关系可后台配置；
- **用户角色可推导**：不为每个用户单独建复杂角色绑定表，用户当前角色由会员状态和会员等级直接推导；
- **后端判定为准**：前端只做体验层拦截，真正放行以接口层为准；
- **兼容平滑迁移**：首期允许保留 `isMember` 兼容字段，但新增角色与权限字段必须作为主口径输出。

### 3.2 现状与改造范围

#### 3.2.1 当前已有能力

- `user_memberships` 已能表达会员起止时间与来源；
- `membership_redeem_code_batches / membership_redeem_codes / membership_redeem_use_logs` 已能支撑兑换码；
- 后台管理员 RBAC 已有完整表结构和管理页，可作为 C 端角色权限页的设计参考；
- `jobs` 页当前已有若干登录/会员拦截点，但口径零散。

#### 3.2.2 当前不足

- `user_memberships` 没有会员等级字段；
- 没有 C 端权限字典表和角色权限关系表；
- `auth-store`、`auth/login`、`auth/me` 都只暴露 `isMember`；
- `jobs` 页权限判断无法精确区分标准与超级会员。

### 3.3 数据模型设计

#### 3.3.1 现有表扩展

1. **`user_memberships` 新增字段**
   - `memberLevel`：会员等级，枚举建议 `standard / super`；
   - 用于表达当前有效会员记录对应的会员层级；
   - 无有效会员记录的用户，角色自动视为 `FREE_USER`。

2. **`membership_redeem_code_batches` 新增字段**
   - `grantLevel`：该批兑换码开通的会员等级；
   - 支持后台按“标准会员卡 / 超级会员卡”发码。

3. **可选兼容字段**
   - `user_memberships.sourceType` 继续保留；
   - `sourceRemark` 继续保留；
   - 后续可在 remark 中标记“升级开通 / 标准续费 / 超级续费”等来源说明。

#### 3.3.2 新增表建议

1. **`member_roles`**
   - 作用：存储 C 端固定角色元数据；
   - 关键字段建议：
     - `id`
     - `code`（固定值：`FREE_USER / STANDARD_MEMBER / SUPER_MEMBER`）
     - `name`
     - `description`
     - `level`（`0 / 1 / 2`）
     - `parentRoleCode`（标准继承免费，超级继承标准）
     - `isSystem`
     - `status`
     - `sort`

2. **`member_permission_catalogs`**
   - 作用：存储 C 端权限字典；
   - 关键字段建议：
     - `id`
     - `permissionKey`
     - `permissionName`
     - `permissionModule`
     - `description`
     - `isSystem`
     - `status`
     - `sort`

3. **`member_role_permissions`**
   - 作用：存储 C 端角色与权限的绑定关系；
   - 关键字段建议：
     - `id`
     - `roleId`
     - `permissionKey`
     - `permissionName`
     - `permissionModule`

#### 3.3.3 为什么不新增 `user_member_roles`

本期只有 3 个固定角色，且用户当前角色可由“是否有有效会员 + 当前会员等级”直接推导：

- 无有效会员：`FREE_USER`
- 有效标准会员：`STANDARD_MEMBER`
- 有效超级会员：`SUPER_MEMBER`

因此本期无需再引入 `user_member_roles` 这种额外绑定表，避免复杂度上升、状态重复、同步出错。

### 3.4 角色与权限解析方案

#### 3.4.1 当前角色解析

建议新增 `MemberAccessService.resolveUserRole(userId)`：

- 查询用户当前有效会员记录；
- 若无记录或已过期，返回 `FREE_USER`；
- 若 `memberLevel = standard`，返回 `STANDARD_MEMBER`；
- 若 `memberLevel = super`，返回 `SUPER_MEMBER`。

#### 3.4.2 有效权限解析

建议新增 `MemberAccessService.resolveEffectivePermissions(roleCode)`：

- 加载当前角色绑定权限；
- 递归合并父角色权限；
- 输出最终权限集合；
- 结果可做本地 TTL 缓存，减少高频读取角色配置表的成本。

#### 3.4.3 鉴权接口返回结构

以下接口建议统一补充：

- `POST /auth/login`
- `POST /auth/register`
- `GET /auth/me`
- `GET /me/overview`
- `GET /me/membership`

新增返回字段建议：

- `memberRoleCode`
- `memberRoleName`
- `memberLevel`
- `permissionKeys`
- `membershipRemainingDays`
- `isMember`（兼容字段，可保留）

### 3.5 后端实现方案

#### 3.5.1 通用能力层

建议新增：

- `apps/api/src/modules/member-access/member-access.service.ts`
- `apps/api/src/modules/member-access/member-access.module.ts`
- `apps/api/src/modules/member-access/decorators/require-member-permission.decorator.ts`
- `apps/api/src/modules/member-access/guards/member-permission.guard.ts`

职责：

- 统一解析用户当前角色；
- 统一解析用户有效权限；
- 统一输出标准 `403` 异常；
- 为各业务模块提供复用式权限拦截。

#### 3.5.2 `jobs` 相关接口接入权限

建议映射如下：

| 接口 / 动作 | 所需权限 |
|---|---|
| `GET /jobs` 获取列表 | `jobs:list:view` |
| `GET /jobs` 传关键词搜索 | `jobs:search:use` |
| `GET /jobs` 传筛选参数 | `jobs:filter:use` |
| `GET /jobs/:id` 或查看公告详情能力 | `jobs:detail:view` |
| `POST /jobs/:id/deliver` | `jobs:deliver:use` |
| `GET /jobs/:id/referral` | `jobs:referral:view` |
| `PUT /jobs/:id/progress` | `jobs:progress:update` |
| `GET /jobs/recommended` | `jobs:recommend:view` |

> 说明：`GET /jobs` 同时承载列表、搜索、筛选，所以后端需要根据请求参数判断额外权限。例如免费用户即使进入了 `jobs` 页面，也不能通过直接拼 query 的方式绕过搜索或筛选限制。

#### 3.5.3 会员开通与续费逻辑改造

- `POST /me/membership/open`：增加 `memberLevel` 参数；
- `POST /me/membership/redeem`：按兑换码批次 `grantLevel` 决定开通等级；
- 后台 `POST /admin/memberships`：支持指定 `memberLevel`；
- 后台 `PATCH /admin/memberships/:id`：支持调整 `memberLevel`。

#### 3.5.4 统一错误码与提示文案

建议后端统一返回：

- `403 + MEMBER_PERMISSION_DENIED`
- 响应体带：
  - `requiredPermission`
  - `requiredRoleCode`
  - `requiredRoleName`
  - `message`

例如：

- `立即投递仅对标准会员及以上开放`
- `查看内推码仅对超级会员开放`
- `专属推荐仅对超级会员开放`

### 3.6 前端实现方案

#### 3.6.1 登录态与全局用户态

当前 `auth-store` 只有：

- `id`
- `phone`
- `name`
- `isMember`
- `inviteCode`

需要升级为：

- `memberRoleCode`
- `memberRoleName`
- `memberLevel`
- `permissionKeys`
- `membershipRemainingDays`
- `isMember`（兼容）

#### 3.6.2 页面与组件侧改造

1. **`jobs-page-client.tsx`**
   - 现有 `requireLogin()` 要升级为 `requirePermission()`；
   - 搜索、筛选、查看公告、投递、内推、进度、推荐 tab 全部走统一权限判断；
   - 标准会员点击超级会员功能时，弹升级引导；
   - 免费用户点击任意核心功能时，弹开通引导。

2. **`membership-open-page-client.tsx`**

### 3.7 后台实现方案

#### 3.7.1 页面规划

1. **新页面：`/admin/member-roles`**
   - 展示 3 个固定角色；
   - 展示权限矩阵勾选；
   - 支持保存配置。

2. **升级现有页面：`/admin/memberships`**
   - 新增 `会员等级` 筛选；
   - 新增 `会员等级` 展示列；
   - 手动开通 / 编辑时可选择 `标准会员 / 超级会员`。

3. **升级现有页面：`/admin/redeem-batches` / `/admin/redeem-codes`**
   - 批次新增 `发放等级` 字段；
   - 区分“标准会员兑换码”和“超级会员兑换码”。

#### 3.7.2 为什么不复用后台管理员角色页

现有 `admin-roles` 页面服务的是后台管理员账号权限，权限码如：

- `dashboard:view`
- `admin:user:manage`
- `admin:membership:manage`

它与 C 端用户的权益能力不是同一维度。若混用：

- 会污染后台治理模型；
- 会让“管理员角色”和“会员角色”语义混乱；
- 会导致运营误操作。

因此必须新增独立的 C 端角色权限页。

### 3.8 缓存与性能建议

- 角色权限矩阵属于低频变更、高频读取数据，建议做进程内 TTL 缓存；
- 缓存 key 可按 `roleCode` 或 `rolesVersion` 设计；
- 后台保存角色权限配置后立即清缓存；
- 用户会员到期判定依然必须基于服务端当前时间实时判断，不依赖长缓存。

### 3.9 种子与迁移方案

#### 3.9.1 数据迁移

- 现有有效会员统一默认迁移为 `STANDARD_MEMBER`；
- 后续如需把部分老会员提升为 `SUPER_MEMBER`，由后台批量工具或 SQL 单独处理；
- 兑换码批次默认补 `grantLevel = standard`，避免历史批次失效。

#### 3.9.2 Seed 初始化

种子中需补充：

- 三个固定 C 端角色；
- 八个系统权限项；
- 三角色的默认权限绑定；
- 至少一条标准会员兑换码批次；
- 至少一条超级会员兑换码批次。

### 3.10 向后兼容方案

- 短期保留 `isMember`，其含义统一为：
  - `memberRoleCode !== FREE_USER`
- 新代码不得再基于 `isMember` 决定具体功能权限；
- 旧逻辑逐步替换为 `permissionKeys.includes(...)` 或后端 guard 校验。

## 五、最终建议与决策说明

### 5.1 为什么这是当前最优方案

- **足够简单**：只保留 3 个固定角色，不引入无限角色扩张；
- **足够清晰**：角色名与用户感知完全一致；
- **足够灵活**：权限项独立可配，后续规则调整无需再到处改页面判断；
- **足够稳**：前后端统一走权限字典与服务端拦截，能避免遗漏与绕过；
- **足够贴合现状**：充分复用当前 `user_memberships`、兑换码、后台 RBAC 设计思路，不推翻重做。

### 5.2 本次拍板后的统一口径

后续所有产品、研发、测试、客服、运营沟通，统一使用以下说法：

- **免费用户**：仅基础浏览，求职核心功能受限；
- **标准会员**：全网岗位随意看，自由搜索筛选、一键投递；
- **超级会员**：全站功能全覆盖，解锁内推码、求职进度、专属岗位推荐。

### 5.3 与后续开发的衔接顺序

建议开发顺序固定为：

1. 先改数据模型与 seed；
2. 再做后端角色解析与接口鉴权；
3. 再做后台配置页；
4. 最后改前端会员页、个人中心与 `jobs` 交互；
5. 联调通过后，再进入 `专属推荐` 等增值能力开发。

---

**结论一句话**：本方案把 Offer360 的会员体系正式收敛为“**三固定角色 + 八颗粒权限 + 超级会员继承标准会员 + 后台可勾选配置 + 前后端双重校验**”的统一底座，可直接作为下一阶段开发实施标准。
