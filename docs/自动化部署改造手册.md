# Offer360 离线镜像部署手册

## 最终方案
- 不使用 Docker Hub、阿里云镜像仓库等任何线上镜像仓库。
- 本地直接构建 `api`、`web`、`wechat-pay-gateway` 三个业务镜像。
- 本地把业务镜像和基础镜像一起导出为离线 `tar` 包。
- 服务器执行 `docker load` 导入镜像，再用 `docker compose` 启动容器。
- 数据库结构不做“本地强制覆盖线上结构”。
- 发布时自动读取线上库当前结构，并与当前代码对应的 Prisma 结构生成 diff。
- 只自动执行安全增量 SQL：新增表、加字段、加索引这类不会破坏已有数据的结构变更。
- 一旦 diff 中出现删表、删字段、字段类型变更、字段重命名、索引删除等危险 SQL，发布立即阻断，并输出差异 SQL 与风险清单，等待人工确认处理。
- 宿主机只开放 `80/443`，由宿主机 `Nginx` 统一反向代理到 `127.0.0.1:3000`。
- 容器不直接对公网开放端口，业务入口长期固定，不随版本更新变化。

## 端口说明
- `13000` / `14000` 仅用于本地开发环境预览，不用于线上部署。
- 本地开发重建脚本 `npm run dev:apps:rebuild` 启动的是开发编排，访问地址是：
  - `http://localhost:13000`
  - `http://localhost:14000/api`
- 当前线上离线部署方案使用的是生产编排 `deploy/prod/docker-compose.yml`，固定端口是：
  - `127.0.0.1:3000 -> web`
  - `127.0.0.1:4000 -> api`
- 公网访问永远只走：
  - `80/443 -> 宿主机 Nginx -> 127.0.0.1:3000`

## 服务器一次性初始化
### 1. 安装 Docker 与 Nginx
```bash
cd /opt/offer360/deploy/prod
sudo bash scripts/install-docker.sh
```

### 2. 初始化部署目录
```bash
cd /opt/offer360/deploy/prod
ENV_FILE=/opt/offer360/.env bash scripts/install-server.sh
```

### 3. 放置 Nginx 站点配置（首次初始化执行）
```bash
sudo cp /opt/offer360/deploy/prod/nginx/offer360.conf /etc/nginx/sites-available/offer360.conf
sudo rm -f /etc/nginx/sites-enabled/default
sudo ln -sf /etc/nginx/sites-available/offer360.conf /etc/nginx/sites-enabled/offer360.conf
sudo nginx -t
sudo systemctl reload nginx
```
- 后续规则：如果 `deploy/prod/nginx/offer360.conf` 有变更，需要重新同步到服务器，并执行：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### 4. 放置证书
- 把 HTTPS 证书放入 `/etc/nginx/ssl/www.offer360.cn`
- 文件名固定：
  - `fullchain.pem`
  - `privkey.pem`
- 把微信支付证书放入 `/opt/offer360/certs`

## 发布脚本会自动完成
- 导入离线镜像包
- 检查 `mysql`、`redis`、`elasticsearch` 是否已处于运行状态；未运行则直接停止发布，不自动启动、不自动重建
- 自动生成“线上当前结构 vs 当前代码结构”的差异 SQL
- 若差异只包含安全增量 SQL，则自动执行结构同步
- 若差异包含危险 SQL，则直接阻断发布，并输出：
  - `deploy/prod/runtime/schema-sync/schema-diff-<tag>.sql`
  - `deploy/prod/runtime/schema-sync/schema-risk-<tag>.txt`
- 启动 `wechat-pay-gateway`、`api`、`web`
- 校验：
  - `http://127.0.0.1:4000/healthz`
  - `http://127.0.0.1:3000/healthz`
- 写入发布状态到 `deploy/prod/runtime/release-state.env`

## 数据库结构同步原则
- 不做“本地结构强制覆盖线上结构”。
- 不允许通过发布脚本自动删线上表、删线上字段、改坏已有字段，避免误伤真实业务数据。
- 自动同步仅覆盖安全增量场景：
  - 新表
  - 新字段
  - 新索引
- 危险变更一律阻断并给出清单，例如：
  - `DROP TABLE`
  - `DROP COLUMN`
  - `DROP INDEX`
  - `MODIFY COLUMN`
  - `CHANGE COLUMN`
  - `ALTER COLUMN`
  - `RENAME TABLE`
  - `RENAME COLUMN`
- 处理原则：
  - 能自动安全补齐的，脚本自动执行
  - 可能影响现网数据的，脚本不执行，只给你 diff 和风险清单
- 线上真实业务数据只保留，不删除、不清空、不覆盖

## 本次踩坑与解决方案
### 1. `docker buildx` 拉取基础镜像超时
- 现象：
  - 本地构建卡在拉取 `node:20-alpine`
  - 常见报错是 `failed to fetch anonymous token`、`i/o timeout`
- 根因：
  - 当前网络环境下 Docker Hub 不稳定，`docker buildx` 直连超时
- 解决方案：
  - 业务 Dockerfile 改成支持基础镜像参数注入
  - `deploy/prod/scripts/package-release.sh` 改为默认使用可达镜像源
  - 本次已验证可用的镜像源是 `docker.m.daocloud.io`

### 2. 离线包在服务器启动时报 `exec format error`
- 现象：
  - `mysql`、`redis`、`elasticsearch` 在服务器反复重启
  - 日志出现 `exec format error`
- 根因：
  - 服务器是 `amd64`，但离线包中的部分基础镜像实际被保存成了 `arm64`
- 解决方案：
  - `deploy/prod/scripts/package-release.sh` 中对基础镜像做平台归一化
  - 重新构建并导出 `amd64` 版本离线包后再上传服务器

### 3. 发布过程长时间停在 `Waiting`
- 结论：
  - 这不一定是 Docker 卡死，通常是 `depends_on` 正在等待依赖服务通过健康检查
- 本次真实根因：
  - `elasticsearch` 健康检查原来用了容器内不可用的 `wget`
  - `wechat-pay-gateway` 健康检查原来检查的是 `/`，但实际健康检查路由是 `/healthz`
- 解决方案：
  - `elasticsearch` 改为：

```yaml
healthcheck:
  test: ["CMD-SHELL", "curl -fsS http://127.0.0.1:9200 >/dev/null"]
```

  - `wechat-pay-gateway` 改为：

```yaml
healthcheck:
  test: ["CMD-SHELL", "wget -q -O- http://127.0.0.1:8080/healthz >/dev/null 2>&1"]
```

- 以后如果再次看到卡在 `Waiting`，按下面顺序查：

```bash
docker compose --env-file /opt/offer360/.env -f /opt/offer360/deploy/prod/docker-compose.yml ps
docker inspect <container_name> --format '{{json .State.Health}}'
docker logs --tail 100 <container_name>
```

### 4. 明明传了新 tag，实际却还是旧镜像
- 现象：
  - 执行 `APP_IMAGE_TAG=<APP_IMAGE_TAG> bash scripts/deploy-release.sh`
  - 日志仍显示旧 tag，例如 `<OLD_APP_IMAGE_TAG>`
- 根因：
  - `deploy-release.sh` 在加载 `/opt/offer360/.env` 后，外部传入的 `APP_IMAGE_TAG` 被旧值覆盖
- 解决方案：
  - 已在 `deploy/prod/scripts/deploy-release.sh` 中修复，显式保留传入的 `APP_IMAGE_TAG`
  - 每次发布完成后，再把服务器 `/opt/offer360/.env` 中的 `APP_IMAGE_TAG` 同步更新为当前线上版本，避免以后手动 `docker compose up` 默认用旧 tag

### 5. `Nginx` 配置正确但 `443` 仍不监听
- 现象：
  - `nginx -t` 通过
  - 站点配置和证书文件都存在
  - 但 `ss -lntp | grep -E ':80|:443'` 只看到 `80`
- 根因：
  - 配置文件已经替换到磁盘，但运行中的 `Nginx` 没有 reload
- 解决方案：

```bash
sudo nginx -t
sudo systemctl reload nginx
ss -lntp | grep -E ':80|:443'
```

- 验证标准：
  - `80` 和 `443` 都能看到 `nginx` 在监听
  - `curl -I http://127.0.0.1 -H 'Host: www.offer360.cn'` 返回跳转
  - `curl -k -I https://127.0.0.1 -H 'Host: www.offer360.cn'` 返回站点响应

  - 避免后续手动执行 `docker compose up -d` 时默认继续使用旧 tag
  - 保证服务器 `.env` 与当前线上实际版本一致

### 4. Nginx 通常不需要改动
- 宿主机 `Nginx` 默认固定代理 `127.0.0.1:3000`
- 常规版本更新只替换镜像和容器，不改 `Nginx` 配置
- 只有在域名策略、证书、反向代理规则变更时，才需要同步 `offer360.conf` 并执行：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

## 注意事项
- 服务器 `.env` 只保留在服务器，不提交仓库。
- 发布前先确认 `/etc/nginx/ssl/www.offer360.cn` 证书已就位。
- 发布前先确认微信支付证书已放入 `/opt/offer360/certs`。
- 发布前先确认生产 `mysql`、`redis`、`elasticsearch` 已在运行；当前发布脚本不会自动启动这 3 个基础服务。
- 每次同步 `deploy/prod/nginx/offer360.conf` 到服务器后，必须执行：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

- 如果 `deploy-release.sh` 报离线包不存在，先检查 `IMAGE_ARCHIVE` 路径。
- 如果 `deploy-release.sh` 报数据库结构同步被阻断，先看：
  - `deploy/prod/runtime/schema-sync/schema-diff-<tag>.sql`
  - `deploy/prod/runtime/schema-sync/schema-risk-<tag>.txt`
- 只要风险清单非空，就表示本次变更包含危险 SQL，当前策略下不会自动执行。
- 如果容器启动失败，优先查看 `docker compose logs -f web api wechat-pay-gateway`。
- 如果发布日志长时间停在 `Waiting`，优先检查依赖服务的健康检查，而不是先判断为 Docker 卡死。
- 如果替换了 Nginx 配置或证书，最后务必执行一次 `sudo systemctl reload nginx`。
- 如果本次线上版本已经切换成功，记得把服务器 `/opt/offer360/.env` 的 `APP_IMAGE_TAG` 同步成当前版本。
