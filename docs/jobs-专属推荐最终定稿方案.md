# Offer360 `jobs` 页专属推荐最终定稿方案

## 一、方案结论（最终拍板口径）

- **产品形态**：继续保留 `jobs` 页内的“全部招聘 / 专属推荐”双 tab 结构，不新增独立频道页。
- **权限口径**：`专属推荐` 调整为 **超级会员专属权益**。仅 `SUPER_MEMBER`（付费或兑换开通且仍在有效期内）的用户可正常查看；`FREE_USER` 与 `STANDARD_MEMBER` 点击后均需弹窗提示并引导前往 `membership` 页面开通或升级。
- **登录口径**：未登录用户点击 `专属推荐` 时先引导登录；登录后若角色仍不是 `SUPER_MEMBER`，则继续执行会员拦截逻辑。
- **角色口径补充**：自 `docs/会员体系最终定稿方案.md` 生效后，本文中与 `专属推荐 / 查看内推码 / 标记求职进度` 相关的“会员专属”表述，统一按 **超级会员专属** 理解；`标准会员` 仅保留列表浏览、搜索筛选、详情查看与立即投递能力。
- **时效口径**：`专属推荐` 仅允许推荐 **近 3 个月内更新** 的招聘公告；技术实现统一按服务端当前时间向前回溯 `90` 天过滤。
- **首期技术路线**：采用 **轻量实时计算 + 规则打分 + 同义词映射 + 小缓存**，不引入 Elasticsearch、协同过滤引擎、离线批处理。
- **数据口径**：首期基于 `UserJobPreferenceTag`、`UserProfile`、`UserJobTracking`、`JobAnnouncement` 四类现有数据实现推荐能力。
- **接口口径**：前端推荐 tab 改为请求独立鉴权接口 `GET /jobs/recommended`，不再通过公开查询参数透传 `userId`。
- **展示口径（2026-04-27 最新）**：`jobs` 页专属推荐列表已取消每条岗位下方的推荐理由/匹配维度 tag 展示，不再显示“匹配意向城市 / 匹配目标岗位 / 学历匹配 / 热度说明”等额外提示；页面仅保留按综合匹配得分降序后的岗位列表与统一操作区，保持版面简洁。
- **配置口径（2026-04-27 最新）**：推荐算法各匹配维度加分值与热度阈值已改为后台单例配置，不再写死在代码中；后台新增 `专属推荐权重配置` 页，管理员可直接调整 `公司 / 岗位 / 城市 / 学历 / 专业 / 时效 / 兜底 / 热度 / 已投递惩罚` 等权重参数并即时生效。
- **地点匹配口径**：严格执行 **“只补父、不展子”**。用户选择城市时，可弱匹配该城市的父级省份岗位；**绝不能**因为同属一个省份，就把其他城市误判为命中。
- **数据采集口径**：全平台所有招聘公告统一接入两类持久化聚合指标：`累计访问点击量`、`岗位投递标记量`。
- **统计口径**：
  - `累计访问点击量`：`查看公告 / 立即投递 / 查看内推 / 更新岗位投递状态` 任一操作触发 1 次，即实时累加；**允许重复计数，不做用户去重**。
  - `岗位投递标记量`：以用户对某岗位形成 **首次有效投递标记** 为准进行累加，避免同一用户反复改状态导致热度虚高。
- **数据改造口径**：首期**不新增独立推荐结果表**，但需为招聘公告增加持久化统计字段；细粒度事件流水表作为二期预留能力。
- **上线目标**：在现有约 `5000` 总用户、`500` DAU、`4` 万岗位、`2C4G` 服务器约束下，先把“推荐可用、结果更准、权限明确、内容更新鲜、统计可积累、后续可扩展”做扎实。

## 二、PRD（最终定稿版）

### 2.1 背景与问题

当前 `jobs` 页虽然已经存在“专属推荐”入口，但现网实现本质上仍是 `GET /jobs` 下的一个查询分支：

- 仅基于 `intentionCompany / intentionJob / intentionCity` 做简单 `contains` OR 过滤；
- 无会员权限隔离、无推荐打分、无推荐理由、无同义词归一化、无缓存；
- 未对招聘公告更新时间做强时效约束，可能把长期未更新岗位继续推给用户；
- 依赖公开参数 `userId` 获取个性化结果，接口边界不清晰；
- 招聘公告缺少统一的点击量、投递标记量持久化统计，后续无法稳定用于热度排序、推荐加权和运营分析；
- 与原 PRD 中“协同过滤 + 内容推荐 + 浏览/投递行为”的描述不一致，容易形成预期落差。

因此本次定稿目标不是追求“大而全”的推荐系统，而是先把“专属推荐”从**弱筛选**升级成**轻量级可解释推荐能力**，同时补齐**会员权限控制、时效过滤和全局公告埋点底座**。

### 2.2 产品目标

#### 2.2.1 核心目标

- **更精准**：推荐结果要明显优于普通列表排序，优先贴合用户意向公司、岗位、城市。
- **更可信**：用户能看到为什么被推荐，且推荐岗位具备基本时效性。
- **更清晰**：明确把 `专属推荐` 定位为会员权益，普通用户不能无门槛查看。
- **更可沉淀**：持续积累公告点击量、投递标记量，为后续热度排序、推荐权重和运营分析提供长期数据资产。
- **更轻量**：在当前基础设施和服务器资源下稳定运行。
- **可扩展**：后续可以平滑接入更多行为信号、缓存、埋点和离线能力。

#### 2.2.2 业务目标

- 提升会员权益感知与会员转化；
- 提升 `专属推荐` tab 的点击率、停留时长、投递转化率；
- 提升个人中心“求职意向”填写率与完善度；
- 降低推荐空列表率、陈旧岗位曝光率与明显误匹配率；
- 建立岗位维度可持续积累的热度数据资产。

### 2.3 目标用户

- **主要用户**：已登录且已开通会员、正在求职的应届生用户；
- **重点人群**：已填写求职意向的会员用户；
- **兼容人群**：已登录但未完善画像或意向的会员用户，也要能看到兜底推荐结果；
- **转化对象**：未开通会员的登录用户，需通过 `专属推荐` 权益拦截完成开通引导。

### 2.4 功能范围

#### 2.4.1 本期包含

- `jobs` 页“专属推荐”tab 的真实推荐化升级；
- `专属推荐` 会员权限隔离；
- `专属推荐` 仅推荐近 `3` 个月内更新岗位；
- 基于意向公司 / 意向岗位 / 意向城市 / 学历 / 专业 / 投递状态的轻量实时推荐；
- 推荐理由展示；
- 结果缓存与缓存失效机制；
- 同义词映射与地点标准化；
- 推荐结果分页、兜底、空态处理；
- 全平台招聘公告 `累计访问点击量`、`岗位投递标记量` 持久化统计；
- 为后续热度排序、推荐热度加权预留数据能力。

#### 2.4.2 本期不包含

- Elasticsearch / 向量检索 / 机器学习排序；
- 真正的协同过滤；
- 全量离线召回、离线特征工程；
- 独立推荐后台运营台；
- 大规模行为埋点明细仓、AB 实验平台；
- 独立推荐结果快照表。

### 2.5 用户流程

#### 2.5.1 会员主流程

1. 会员用户登录后进入 `jobs` 页；
2. 点击“专属推荐”；
3. 系统校验会员有效期；
4. 服务端读取用户画像、求职意向、岗位投递状态；
5. 系统自动过滤 `90` 天前更新的岗位；
6. 服务端实时召回候选岗位并完成打分排序；
7. 前端展示推荐结果及“推荐理由”；
8. 用户继续筛选、查看公告、投递、查看内推、更新进度；
9. 点击与投递标记数据同步累计沉淀。

#### 2.5.2 未登录流程

- 点击“专属推荐”时，引导登录；
- 登录后回到 `jobs` 页并默认进入推荐 tab；
- 若登录后不是会员，则继续进入会员拦截弹窗。

#### 2.5.3 非会员流程

- 已登录但非会员用户点击“专属推荐”；
- 系统弹窗提示：`专属推荐为会员专属权益，请先开通会员后查看`；
- 弹窗提供 `立即开通会员` 主按钮，跳转 `/membership`；
- 非会员用户不可获取推荐列表数据。

### 2.6 交互与页面规则

#### 2.6.1 入口与结构

- 保持现有顶部 tab：`全部招聘` / `专属推荐`；
- 点击 `专属推荐` 时先完成登录校验、会员校验；
- 会员通过校验后，仍沿用当前规则：**自动清空旧筛选项**，回到推荐默认列表；
- 推荐 tab 下仍支持用户继续使用搜索和筛选项做二次收敛。

#### 2.6.2 推荐卡片新增信息

每条推荐岗位新增 `1~2` 个推荐理由 tag，例如：

- `匹配意向公司：烟草`
- `匹配目标岗位：产品`
- `匹配意向城市：南京`
- `匹配你的专业：计算机`
- `近 3 天发布`
- `岗位热度较高`

展示原则：

- 默认只展示分值最高的前 `2` 条推荐理由；
- 不直接展示内部 score 数值；
- 推荐理由必须是用户能理解的自然语言，不暴露算法细节；
- `岗位热度较高` 仅在点击量/投递量达到阈值后展示，避免低样本误导。

#### 2.6.3 权限拦截交互

- **未登录**：提示“登录后即可体验会员专属推荐”；
- **已登录但非会员**：展示会员弹窗，说明 `专属推荐为会员专属权益`；
- **会员已过期**：按非会员逻辑处理，不允许继续查看旧推荐结果缓存；
- **会员开通成功**：返回 `jobs` 页后可直接进入 `专属推荐`。

#### 2.6.4 空态与弱画像处理

- **会员但无求职意向**：提示“完善求职意向后，推荐会更精准”，同时展示兜底推荐列表；
- **命中结果过少**：自动混入平台精选岗位补足分页，但仍必须满足近 `3` 个月更新限制；
- **没有任何符合时效条件的数据**：展示空态文案 `当前暂无符合时效条件的推荐岗位，请稍后再来查看`。

### 2.7 核心业务规则

#### 2.7.1 会员权限规则

- `专属推荐` 为**会员专属权益**；
- 有效会员定义：存在 `UserMembership`，且 `endAt >= 服务端当前时间`；
- 会员来源包括付费开通与兑换码开通；
- 非会员或已过期会员请求推荐接口时，服务端返回 `403`；
- 前端不得通过本地 `isMember` 字段绕过校验，必须以后端鉴权结果为准。

#### 2.7.2 时效过滤规则

- `专属推荐` 只推荐 `updatedAt >= now - 90 days` 的招聘公告；
- 超过 `90` 天未更新的岗位，即使匹配度高，也不得出现在推荐结果中；
- 兜底推荐同样必须满足该时效约束；
- 普通 `全部招聘` 列表不强制沿用本规则，避免影响既有全量浏览能力。

#### 2.7.3 推荐维度

首期采用以下维度：

- **强维度**：意向公司、意向岗位、意向城市；
- **中维度**：学历、专业；
- **弱维度**：岗位新鲜度、企业性质、岗位热度、用户已投递状态。

#### 2.7.4 地点匹配规则（最终口径）

地点匹配采用 **“只补父、不展子”**：

- 用户意向为 `南京`：
  - **强命中**：`南京`；
  - **弱命中**：`江苏`、`江苏省` 这类父级范围描述；
  - **不命中**：`苏州`、`无锡` 等其他同省城市。
- 用户意向为 `江苏`：
  - 只匹配岗位文本中明确包含 `江苏` / `江苏省` 的岗位；
  - **不自动扩展**到全省所有城市岗位，除非岗位文本本身明确写出该城市或省级范围。

该规则必须贯穿召回、打分和推荐理由生成，避免“同省错配”。

#### 2.7.5 已投递岗位处理

- 对用户已有 `UserJobTracking` 记录的岗位不做硬过滤；
- 但若状态已是 `已投递 / 已笔试 / 已面试 / 已录用`，则在推荐排序中**降权**，让更多未处理岗位优先展示；
- 用户仍可在推荐列表中查看并维护进度；
- 若用户通过 `立即投递` 触发系统自动标记 `已投递`，也视为该岗位已形成有效投递标记。

#### 2.7.6 访问点击统计规则

只要用户点击某条招聘公告操作区域内任一功能按钮，即记为该公告 `1` 次访问点击并实时累加：

- `查看公告`
- `立即投递`
- `查看内推 / 内推码`
- `更新岗位投递状态`

说明：

- 同一用户、多次点击、跨页面重复点击，均允许正常累计；
- 不做用户去重；
- 同一次业务动作只累计 `1` 次访问点击，不因前后端多次请求重复记数；
- 统计口径面向 **公告级别**，不是页面 PV。

#### 2.7.7 投递标记统计规则

`岗位投递标记量` 以用户对该岗位形成**首次有效投递标记**为准：

- 用户首次通过 `立即投递` 形成 `已投递` 状态，记 `1` 次；
- 用户首次通过手动更新岗位进度，把状态从 `未标记` 变更为任一有效状态，记 `1` 次；
- 同一用户对同一岗位后续再次改状态（例如 `已投递 -> 已笔试 -> 已面试`），**不重复累加**；
- 本指标用于表达岗位实际投递热度，不允许被同一用户反复操作无限放大。

#### 2.7.8 兜底策略

当用户画像不足或召回结果不够时，按以下顺序补足：

1. 高匹配但数量不足的推荐结果；
2. 平台近 `7` 天较新的央企 / 国企岗位；
3. 近 `7` 天高质量通用岗位；
4. 最终仍不足时，按热度与更新时间综合排序补齐；
5. 以上全部候选均必须满足 `90` 天时效限制。

### 2.8 推荐算法口径（产品视角）

#### 2.8.1 召回策略

服务端从现有岗位库中召回五类候选集：

- **公司召回**：按意向公司及其别名匹配 `companyName`；
- **岗位召回**：按意向岗位及其别名匹配 `positionNames / positionCategory`；
- **地点召回**：按地点标准化结果匹配 `workLocation`；
- **画像补充分**：基于专业、学历做二次筛选与加分；
- **兜底召回**：近 `7` 天平台精选岗位。

候选集合并去重后进入打分阶段，避免直接对全量岗位做复杂排序。

#### 2.8.2 排序策略

采用规则打分模型：

- 意向公司命中：高权重；
- 意向岗位命中：高权重；
- 地点命中：高权重，其中“城市精确命中”高于“父级省份弱命中”；
- 学历匹配：中权重；
- 专业匹配：中权重；
- 近更新岗位：低权重加分；
- 岗位热度：低权重加分；
- 已投递岗位：负向权重；
- 若分值相同，按 `updatedAt desc`。

#### 2.8.3 推荐可解释性

推荐结果必须同步返回 `recommendReasons`，且理由来源只能是本次真实命中的维度，不允许生成虚假解释。

### 2.9 成功指标

#### 2.9.1 核心指标

- `专属推荐` tab 点击率；
- 非会员被拦截后的会员开通转化率；
- 推荐岗位详情点击率；
- 推荐岗位投递转化率；
- 推荐列表空结果率；
- 用户求职意向填写率；
- 推荐结果中过期岗位曝光率（目标为 `0`）。

#### 2.9.2 公告数据指标

- 公告累计访问点击量；
- 公告累计投递标记量；
- 点击量 TOP 榜单；
- 投递量 TOP 榜单；
- 点击转投递比。

#### 2.9.3 观察指标

- 推荐接口平均耗时；
- 推荐缓存命中率；
- 推荐列表首屏返回岗位数；
- 推荐结果中“已投递岗位占比”；
- 埋点接口成功率与统计延迟。

### 2.10 验收标准

- 登录用户可稳定打开 `专属推荐`，接口不再依赖公开 `userId`；
- 非会员访问 `专属推荐` 时，被准确拦截并引导开通会员；
- 推荐接口返回结果全部满足 `updatedAt >= now - 90 days`；
- 填写不同意向的两个会员测试账号，推荐结果有明显差异；
- 推荐结果排序不再仅按 `updatedAt`，而是先按推荐分排序；
- 每条推荐结果能返回至少 `1` 条真实推荐理由；
- 用户修改意向后，推荐缓存会失效并更新；
- 地点匹配满足“只补父、不展子”；
- 点击 `查看公告 / 立即投递 / 查看内推 / 更新岗位投递状态` 任一操作，公告点击量都会成功累加；
- 同一用户首次形成有效投递标记时，公告投递标记量成功累加；后续重复改状态不重复累计；
- 单次请求在当前数据规模下可控，不引入明显卡顿。

## 三、技术实施方案（最终定稿版）

### 3.1 总体设计

本期采用 **“独立推荐接口 + 轻量推荐服务 + 公告指标服务 + 进程内缓存”** 的实现结构：

- `JobsController` 新增鉴权接口 `GET /jobs/recommended`；
- 推荐逻辑从当前 `JobsService.buildWhere()` 中拆出，收敛到独立推荐服务；
- 推荐服务入口必须增加会员校验与 `90` 天时效过滤；
- 普通岗位列表 `GET /jobs` 保持职责纯净，继续负责全量列表、筛选、分页；
- 新增公告指标服务，统一处理点击量与投递标记量累计；
- 首期使用 **Node 进程内 LRU / TTL 缓存**，后续再平滑升级 Redis。

### 3.2 数据设计

#### 3.2.1 直接使用的现有表

- `job_announcements`：岗位主数据；
- `user_job_preference_tags`：意向城市 / 岗位 / 公司；
- `user_profiles`：学历、专业等画像；
- `user_job_tracking`：投递/进度行为；
- `user_memberships`：会员身份与有效期校验。

#### 3.2.2 本期数据结构改造

建议在 `job_announcements` 增加以下持久化字段：

- `accessClickCount`：公告累计访问点击量，`INT NOT NULL DEFAULT 0`
- `deliveryMarkCount`：公告累计投递标记量，`INT NOT NULL DEFAULT 0`
- `lastAccessAt`：最近一次访问点击时间，`DATETIME NULL`
- `lastDeliveryMarkAt`：最近一次形成有效投递标记时间，`DATETIME NULL`

说明：

- 这四个字段用于承载稳定、可直接查询的聚合结果；
- 首期优先采用聚合字段，满足排序、推荐加权和后台分析；
- **不强制新增事件明细表**，避免在当前资源条件下把方案做重；
- 若二期需要用户级明细漏斗，再补 `job_announcement_action_logs` 之类的流水表。

#### 3.2.3 为什么不先上独立事件仓

- 当前核心目标是先把聚合指标稳定积累起来；
- 现有 DAU 与机器配置不适合优先建设重型埋点体系；
- 推荐权重、热度排序与基础运营分析，聚合指标已足够支撑首期上线。

### 3.3 后端模块设计

#### 3.3.1 推荐服务拆分建议

建议在 `apps/api/src/modules/jobs/` 下新增以下文件：

- `jobs-recommendation.service.ts`：推荐主服务；
- `jobs-recommendation.types.ts`：推荐候选、分数、理由类型；
- `jobs-recommendation.constants.ts`：权重、阈值、缓存 TTL 等常量；
- `jobs-recommendation-synonyms.ts`：同义词词典；
- `jobs-recommendation-location.ts`：地点标准化与“只补父、不展子”匹配工具；
- `jobs-recommendation-cache.ts`：缓存封装；
- `jobs-metrics.service.ts`：公告点击量 / 投递标记量聚合统计服务。

#### 3.3.2 接口设计

##### 新增接口

- **`GET /jobs/recommended`**
  - **鉴权**：必须登录；
  - **权限**：必须为有效会员；
  - **参数**：`page`、`limit`，以及与普通列表一致的可选筛选参数；
  - **不再接收**：`userId`、`tab`；
  - **用户身份来源**：JWT。

- **`POST /jobs/:id/click`**
  - **用途**：用于 `查看公告` 场景记录一次公告访问点击；
  - **Body**：`{ actionType: 'view_announcement' }`
  - **鉴权**：可不强制登录；若已登录可附带用户上下文做日志扩展，但不影响聚合口径。

##### 复用并增强现有接口

- **`POST /jobs/:id/deliver`**
  - 记录 `1` 次访问点击；
  - 同步把当前用户该岗位状态写为 `已投递`；
  - 若这是该用户对该岗位形成的首次有效投递标记，则公告 `deliveryMarkCount + 1`。

- **`GET /jobs/:id/referral`**
  - 记录 `1` 次访问点击；
  - 继续保留会员门禁。

- **`PUT /jobs/:id/progress`**
  - 记录 `1` 次访问点击；
  - 更新岗位进度；
  - 若状态从 `未标记` 首次进入有效状态，则公告 `deliveryMarkCount + 1`。

#### 3.3.3 返回结构建议

`GET /jobs/recommended` 返回结构建议：

```json
{
  "list": [
    {
      "id": "job-id",
      "companyName": "某央企",
      "positionNames": "产品经理",
      "workLocation": "南京",
      "currentProgress": "未标记",
      "recommendReasons": ["匹配目标岗位：产品", "匹配意向城市：南京"],
      "recommendMeta": {
        "hitDimensions": ["job", "location"],
        "version": "v1"
      },
      "accessClickCount": 128,
      "deliveryMarkCount": 23
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 128,
    "hasMore": true
  }
}
```

#### 3.3.4 会员校验实现

- 推荐接口服务端通过 `userId` 查询 `user_memberships`；
- 使用现有 `isMembershipActive` 统一判断是否有效；
- 非会员或会员过期时，抛出统一业务异常：`专属推荐为会员专属权益，请先开通会员`；
- 前端收到 `403` 后弹出会员引导弹窗并跳转 `/membership`。

#### 3.3.5 时效过滤实现

- 推荐服务在召回前先构造基础过滤条件：`updatedAt >= subDays(now, 90)`；
- 所有召回分支、兜底分支、热度补足分支都共享这层基础 where；
- 该约束位于服务端，不允许仅靠前端兜底过滤。

#### 3.3.6 缓存设计

- **缓存维度**：`userId + membershipState + page + limit + filtersHash + recommendVersion`；
- **TTL**：建议 `10` 分钟；
- **缓存内容**：推荐结果 ID 列表、理由摘要、总数；
- **失效时机**：
  - `PUT /me/profile`
  - `PUT /me/preferences`
  - `POST /jobs/:id/deliver`
  - `PUT /jobs/:id/progress`
  - 会员开通 / 续期 / 过期
- **实现方式**：首期进程内 LRU；后续如有多实例再抽象到 Redis。

#### 3.3.7 召回策略

为兼顾性能与效果，采用“先召回、后打分”：

1. 校验登录、会员状态；
2. 读取用户画像与意向；
3. 构造近 `90` 天岗位基础集合；
4. 对公司、岗位、地点做标准化和同义词扩展；
5. 使用 Prisma 生成多个轻量候选查询；
6. 合并候选集并去重；
7. 对候选集进行应用层打分；
8. 排序后分页返回。

建议候选规模控制：

- 单个维度召回结果上限 `150 ~ 200`；
- 合并后总候选上限 `300 ~ 500`；
- 避免直接对全量 `4` 万岗位做复杂逻辑计算。

#### 3.3.8 打分模型（建议权重）

建议采用如下首版权重：

- **意向公司命中**：`+35`
- **意向岗位命中**：`+30`
- **意向城市精确命中**：`+20`
- **意向城市父级省份弱命中**：`+10`
- **学历匹配**：`+8`
- **专业匹配**：`+8`
- **近 3 天发布**：`+6`
- **近 7 天发布**：`+3`
- **岗位热度加分**：`+0 ~ +6`（由 `deliveryMarkCount`、`accessClickCount` 归一化后提供）
- **央企 / 国企兜底加分**：`+4`
- **已投递/已推进岗位**：`-12`

说明：

- 同一维度多次命中可累计，但需要设置总分上限，避免某一维度过度放大；
- `graduationYear` 本期不纳入打分，因为岗位侧暂无对应标准化字段；
- `majorRequirement` 只参与打分，不建议参与重召回，避免文本匹配开销过大；
- 热度权重必须是弱权重，不能压过用户意向主权重。

#### 3.3.9 同义词策略

首期采用**人工维护的小词典**，只覆盖高频、高价值词，不做大词库扩展。

建议样例：

- 公司词：`烟草 -> [中烟, 烟草公司]`
- 岗位词：`产品 -> [产品经理, 产品运营]`
- 岗位词：`开发 -> [研发, 软件开发, 前端, 后端]`
- 地点词：统一处理 `南京` / `南京市`、`江苏` / `江苏省` 等标准化映射。

控制原则：

- 同义词宁少勿滥；
- 不允许为了扩大召回而引入明显误配词；
- 每次运营新增词典时，必须带测试样例。

#### 3.3.10 公告指标统计实现

##### 点击量统计

统一由 `JobsMetricsService.recordAccessClick(jobId, actionType)` 处理：

- `查看公告`：前端先调用 `POST /jobs/:id/click`，成功后再执行 `window.open`；
- `立即投递`：在 `deliver()` 服务内自动调用；
- `查看内推`：在 `getReferral()` 服务内自动调用；
- `更新岗位投递状态`：在 `updateProgress()` 服务内自动调用。

##### 投递标记量统计

统一由 `JobsMetricsService.recordDeliveryMark(jobId, userId)` 处理：

- 核心判断依据是 `user_job_tracking` 当前是否已存在有效投递标记；
- 若首次从 `未标记` 进入有效状态，则原子性执行 `deliveryMarkCount + 1`；
- 若已存在有效标记，则不再重复加数；
- 必须使用事务或原子更新，避免并发重复累加。

#### 3.3.11 与现有代码的衔接方式

当前代码中，推荐逻辑仍写在 `jobs.service.ts` 的 `buildWhere()` 中，且通过 `query.userId` 查 `userJobPreferenceTag`。本次改造后的边界应为：

- `JobsService.getList()`：继续处理普通列表；
- `JobsRecommendationService.getRecommendedList(userId, query)`：处理会员专属推荐列表；
- `JobsMetricsService`：统一处理公告点击量与投递标记量；
- `QueryJobsDto`：保留普通列表参数，但去掉推荐链路对 `userId/tab` 的依赖；
- `docs/api-contract.md`：同步更新接口说明；
- `UserJobTracking`：继续复用当前 `uniq_user_job_tracking` 作为用户-岗位维度的投递状态唯一约束。

### 3.4 前端实施方案

#### 3.4.1 页面与交互改动

前端继续以 `jobs-page-client.tsx` 为主承载，但做以下调整：

- 推荐 tab 请求从 `/jobs?tab=recommended&userId=...` 切换为 `/jobs/recommended`；
- 不再向前端 query 中透传 `userId`；
- 点击推荐 tab 时先处理登录与会员拦截；
- 列表项新增 `recommendReasons` 展示区；
- 列表项可展示 `访问量 / 投递量` 等轻量热度标签（如需要可灰度开启）；
- 登录跳转回来后可恢复到推荐 tab；
- 推荐 tab 的空态文案、会员引导文案做差异化展示。

#### 3.4.2 查看公告链路改造

当前 `查看公告` 按钮直接 `window.open(job.announcementUrl)`，无法自然沉淀后端统计；因此需要改为：

1. 前端点击 `查看公告`；
2. 调用 `POST /jobs/:id/click`；
3. 成功后再 `window.open` 外链；
4. 若埋点接口失败，可降级仍打开链接，但需记录前端错误日志。

#### 3.4.3 SSR / CSR 口径

- `jobs` 页首屏 SSR 仍只拉普通 `全部招聘` 列表；
- `专属推荐` 因依赖登录态、会员态与个性化计算，继续采用客户端请求；
- 不追求首屏 SSR 推荐，避免服务端鉴权与缓存复杂度上升。

### 3.5 数据消费方案

首期数据消费建议：

- `全部招聘`：暂不强依赖点击量/投递量排序，避免影响现有体验；
- `专属推荐`：把热度作为**弱权重**参与推荐；
- 后台运营：后续可新增热度排序、热榜导出、热门岗位筛选；
- 数据分析：基于聚合字段输出公告热度快照。

### 3.6 性能与风险控制

#### 3.6.1 性能控制

- 候选集控制在 `300 ~ 500`；
- 对文本字段匹配优先走公司、地点、岗位三大强维度；
- 使用缓存降低重复计算；
- 推荐分页在打分排序后执行，避免每次只算当前页带来排序失真；
- 点击量与投递量采用原子自增，避免读后写放大。

#### 3.6.2 风险点

- **误匹配风险**：同义词放太宽；
- **地点错配风险**：省市逻辑处理不严谨；
- **权限绕过风险**：只靠前端做会员拦截；
- **性能波动风险**：候选集过大、频繁无缓存请求；
- **统计失真风险**：同一次操作重复计数，或投递标记被重复累计；
- **查看公告丢点风险**：外链先打开导致统计请求未落地。

#### 3.6.3 风险应对

- 同义词只上小词典；
- 地点规则独立封装并加单测；
- 会员权限以后端鉴权为准；
- 推荐理由与打分逻辑共用同一份命中结果；
- 推荐版本号纳入缓存 key，方便后续调整规则后整体失效；
- 点击统计采用统一 service；
- 投递标记采用 `userId + jobId` 唯一约束 + 事务更新；
- `查看公告` 采用“先打点、后跳转”的前端时序。

- 已投递岗位在推荐列表中明显后移；
- 推荐理由与实际命中维度一致。

#### 埋点测试

- 点击 `立即投递`，点击量 `+1`；首次形成有效投递标记时，投递量 `+1`；

#### 性能测试

- 热缓存命中耗时；
- 连续翻页场景；
- 高频修改意向后的缓存失效场景；

## 五、上线建议

### 5.1 推荐上线顺序

- **第 1 步**：先在开发环境完成推荐接口、会员门禁和公告统计联调；
- **第 2 步**：用 `3~5` 个不同画像账号与 `2~3` 个非会员账号做人工验收；
- **第 3 步**：灰度观察非会员拦截率、会员转化、推荐空列表率、接口耗时、统计自增是否准确；
- **第 4 步**：稳定后再逐步把点击量/投递量接入更多后台运营视图与排序能力。

### 5.2 二期预留方向

- 公告行为明细事件表；
- 更精细的岗位点击行为信号；
- 管理后台同义词词典维护；
- Redis 多实例缓存；
- 更丰富的运营精选池与排序策略；
- 基于点击量/投递量的热门岗位榜单与后台分析面板。

## 六、一句话总结

本次“专属推荐”最终定稿方案的核心，不是一次性做成重型推荐系统，而是基于 Offer360 当前真实数据和资源约束，把现有 `recommended` 弱筛选升级为 **有会员边界、有时效底线、有热度数据沉淀、可解释、可扩展、可上线的轻量推荐能力**：**会员门禁、90 天过滤、独立接口、服务端识别用户、规则打分、地点精匹配、小词典、小缓存、公告点击量与投递标记量持久化**。
