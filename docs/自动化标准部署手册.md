## 本次环境核查结论
- 当前线上项目没有脱离宝塔面板另起一套独立环境，仍运行在最初的 `宝塔 Nginx + Docker Compose` 架构内。
- 业务代码、发布脚本、运行状态、发布记录都集中在服务器目录：`/opt/offer360`。
- 当前版本迭代方式虽然改成了命令行上传和执行脚本，但本质上只是对同一套 `docker-compose.yml` 做镜像更新与容器重建，不是新建第二套项目。
- 宝塔当前承担的职责仍然是：公网 `80/443` 入口、站点 Nginx 配置、证书目录与续签后的证书加载。
- Docker 当前承担的职责仍然是：运行 `mysql`、`redis`、`elasticsearch`、`wechat-pay-gateway`、`api`、`web` 这些生产容器。
- 当前公网访问链路已核实为：`80/443 -> 宝塔 Nginx -> 127.0.0.1:3000 -> web 容器`，`api` 仅绑定 `127.0.0.1:4000` 供反向代理与内部调用使用。
- 当前标准结论应固定为：`宝塔负责入口与证书，命令行脚本负责版本迭代，Docker Compose 负责业务运行`。

## 标准部署方式
- 唯一标准生产部署方式：`本地 package-release.sh -> 上传离线 tar -> 服务器 deploy-release.sh`。
- 宝塔面板不是业务镜像发布入口，不再通过宝塔重新创建项目、重新拉起另一套 Docker、重新指定另一套站点目录。
- 宝塔后续只用于站点入口维护、Nginx 配置调整、证书续签与基础巡检；业务版本升级、回滚、发布记录写入统一走 `deploy/prod/scripts/*.sh`。
- 只要继续沿用 `docker-compose.yml`、`/opt/offer360/.env`、`/opt/offer360` 数据目录和宝塔站点反代配置，后续迭代不会因为“命令行发布”与“宝塔部署”产生双轨冲突。

## 核心原则
- 不使用线上业务镜像仓库，业务镜像走本地构建 + 离线 `tar` 上传。
- 宝塔面板是统一运维入口，公网流量统一进入宝塔 Nginx。
- Docker 容器禁止直接占用公网 `80/443`。
- 生产容器只绑定宿主机本地端口，由宝塔 Nginx 反向代理。
- 发布只允许安全增量结构同步，危险 SQL 一律阻断。
- 业务迭代只允许更新 `/opt/offer360` 这一套生产目录，不再新增第二套项目目录或第二份生产 compose。
- 不允许在宝塔中再次新建一个同域名 Docker 站点或把业务容器改成直接监听公网端口，否则会与现有入口和证书配置冲突。

### 当前实际策略
- Certbot 原始证书目录：`/etc/letsencrypt/live/offer360.cn`

- 已安装 deploy hook：`/etc/letsencrypt/renewal-hooks/deploy/offer360-bt-sync.sh`

### 为什么要同步
- Certbot 续签后只更新 Let’s Encrypt 目录。
- 宝塔 Nginx 读取的是宝塔证书目录。
- 所以续签后必须把证书复制到宝塔目录并 reload Nginx。

### 手动同步命令
```bash
sudo /usr/local/bin/sync-bt-cert.sh offer360.cn www.offer360.cn
```

## 宝塔 Nginx 配置
### 当前正式配置
```text
/www/server/panel/vhost/nginx/offer360.conf
```

### 入口层缓存要求
- `offer360.conf` 必须直接反向代理到 `127.0.0.1:3000`，且站点级 `location /` 与 `location ^~ /_next/static/` 必须显式关闭代理缓存。
- 原因：宝塔全局 Nginx 默认可能启用 `proxy_cache`；如果对 Next.js 页面 HTML 或 `/_next/static` 资源做了代理缓存，公网入口可能继续返回旧版 HTML，进而引用已经失效的页面级 chunk，表现为“页面跳转后布局错乱、样式异常、组件未正常加载”。
- 若线上 `127.0.0.1:3000` 直连正常，但正式域名仍引用旧的 `/_next/static/chunks/app/...page-*.js`，应优先判定为宝塔入口缓存问题，而不是浏览器缓存问题。

### 同步并生效
```bash
scp -i "/Users/maizim/Documents/2605GPT54offer360/云服务器登陆密钥.pem" \
  /Users/maizim/Documents/2605GPT54offer360/deploy/prod/nginx/offer360.conf \

```

### 4. 发布脚本自动完成的动作
- 导入离线业务镜像。
- 校验 `schema.prisma`、`migrations`、`infra/sql/schema.sql` 一致性。
- 先做数据库备份，再生成线上结构差异 SQL。
- 仅在安全前提下执行增量结构同步。
- 仅清理 `web`、`api`、`wechat-pay-gateway` 旧容器、悬空镜像与 builder 缓存，不触碰 `mysql`、`redis`、`elasticsearch` 数据卷。
- 强制重建 `wechat-pay-gateway`、`api`、`web` 三个业务容器。
- 自动校验 `http://127.0.0.1:4000/healthz` 与 `http://127.0.0.1:3000/healthz`。
- 自动抓取关键路由 HTML：`/`、`/resume-optimizer`、`/interview-transcript`。
- 同时校验本地入口 `http://127.0.0.1:3000` 与公网入口 `https://www.offer360.cn` 上述关键路由引用的 `/_next/static/*.css|js` 资源都能返回 `200`，否则发布失败。
- 自动校验公网 `robots.txt` 与 `sitemap.xml`：必须输出正式域名、不得包含 `localhost/127.0.0.1`，且 sitemap 必须包含首页、服务列表页与至少一个服务详情页 URL。
- 通过后写入 `deploy/prod/runtime/release-state.env`。
- 自动清理旧业务镜像、旧离线包、旧数据库备份。

## 注意事项
- 服务器 `.env` 只保留在服务器，不提交仓库。
- 发布前必须确认微信支付证书已放入 `/opt/offer360/certs`。
- 发布前必须确认生产基础服务已运行。
- 只要结构风险清单非空，本次发布就不能自动执行危险 SQL。
- 如果首页没有解析出 CSS，或首页引用的任一 `/_next/static/*.css|js` 资源不是 `200`，应直接判定为发布结果异常，不要误判成“前端只是浏览器缓存问题”。
- 如果 `127.0.0.1:3000` 与正式域名返回的关键路由 HTML 中页面级 chunk 名称不一致，应优先排查宝塔 Nginx 代理缓存、站点配置未 reload 或入口层仍命中旧缓存。
- 如果 `robots.txt` / `sitemap.xml` 中仍出现 `localhost`、`127.0.0.1` 或 sitemap 没有服务详情页 URL，应直接判定为发布结果异常，不要把问题留到搜索引擎收录阶段再补救。
- 后续不要把“宝塔管理”理解为“要在宝塔里重新部署一套应用”。当前宝塔只管理入口层，业务版本切换必须继续走脚本。
- 后续不要在新目录重复上传另一份项目、不要重新创建第二份同域名站点、不要让容器直绑公网 `80/443`，否则最容易造成目录错乱、端口冲突、证书错配和流量走错实例。
- 如果需要做数据备份，优先使用发布脚本自带的发布前数据库备份，并配合 Docker volume 级备份；不要因为版本迭代另建新库或切换 `DATABASE_URL` 指向。
- 如果需要重新部署整站，也应先恢复 `/opt/offer360` 这套目录、`.env`、证书目录和宝塔反向代理配置，再执行标准发布脚本，不要混用第二套部署方式。
- 每次替换宝塔 Nginx 配置或证书后，都要执行：

```bash
sudo /usr/bin/nginx -t
sudo /etc/init.d/nginx reload
```
